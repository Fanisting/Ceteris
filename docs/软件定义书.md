# Ceteris 软件定义书

> 一个 Windows 平台首发、跨平台架构 ready 的、以路径为中心的、对 AI agent 友好的桌面终端管理器
>
> 文档版本:1.6 · 最后更新:2026-05-16

> **改名说明**:本产品在 alpha 阶段(CP-1 至 Milestone 1)的开发代号为 **EasyTerm**,自 v1.5 起正式定名 **Ceteris**。本文档与 `AGENTS.md` / `ipc-protocol.md` 已同步替换"产品现状"维度的称呼;`docs/checkpoints/`、各勘误档、工作记录等历史档保留 EasyTerm 字样作为决策快照。代码层归档格式同时接受新名 `ceteris-archive` 和旧名 `easyterm-archive`,向后兼容。详见 ADR-012。

## 1. 产品定位

Ceteris 是一个 **Windows 平台的桌面终端管理器**,服务于"在多个不同路径下并发运行多个长时间任务(包括 AI coding agent 和普通命令行任务)"的开发者。

它**不是**一个传统终端模拟器的迭代,而是对"终端会话应该如何被管理"这个问题的重新回答:

* 传统终端把"窗口生命周期"和"shell 进程生命周期"绑定 —— 关窗即死。
* 传统终端以"profile / tab"为组织维度 —— 用户需要靠记忆和手动 cd 来导航。
* 传统终端假设用户是命令行专家 —— 重度依赖快捷键和配置文件。

Ceteris 反其道而行:

* **会话独立于 UI 存活** —— 关掉所有窗口,会话仍在守护进程内运行,直到用户主动结束。
* **路径作为一等公民** —— 所有终端按"工作位置"组织,不再按 profile 或 project。
* **GUI 优先** —— 用户从不需要手敲路径,从不需要记忆快捷键,所有操作都可以用鼠标完成。

### 一句话定位

> "你的终端会话不应该因为关掉窗口就死掉。"

## 2. 设计哲学

Ceteris 的所有设计决策都源自四条核心原则:

### 原则 1:Path 是稳定的,Session 是廉价的,UI 是临时的

| 层级 | 性质 | 用户对它的态度 |
|------|------|--------------|
| Path(路径) | 长期、稳定、用户主动管理 | 收藏、命名、组织 |
| Session(会话) | 短期、用完即弃、自动产生与销毁 | 启动、使用、关闭 |
| UI 窗口 | 完全临时、可随时开关、彼此平等 | 打开看一眼,不用了关掉 |

**这条原则推导出**:
* 三栏侧栏分类(收藏/临时/最近)以 path 为单位
* session 不维护跨会话的累积上下文
* 关闭窗口完全不影响 session
* 守护进程持有所有 session 和数据,窗口只是"观察窗"

### 原则 2:不让用户输入路径,只让用户点击路径

`cd` 命令是一个 1971 年的设计,它打错就报错或静默进入错误位置,代价高昂。Ceteris 把"切换工作位置"重构为"点击一个已存在的路径条目",彻底绕过文本输入路径这个易错动作。

**这条原则推导出**:
* 所有路径必须通过文件夹选择器或 Explorer 拖入,不能手敲
* 路径在 UI 上永远可见,用户不需要 `pwd` 校对
* 切换路径 = 点击侧栏 = 启动新会话或聚焦已有会话,而不是 `cd`

### 原则 3:用户决策最少化

工具应该自动处理一切可以自动处理的事,只在用户必须做选择时才打扰用户。

**这条原则推导出**:
* 路径在三个分类之间的流转完全自动(状态机驱动)
* session 标签在路径间的归属由 cwd 自动决定(OSC 1337 hook)
* 终端切换时的 resize 自动发生
* 状态指示自动检测,不需要用户配置
* 所有窗口平等,没有"主次"概念,用户不需要思考"我该关哪个"

### 原则 4:窗口与应用解耦

应用 ≠ 窗口。窗口是临时的观察工具,应用是承载所有 session 的守护进程 + 托盘。

**这条原则推导出**:
* 关闭任何一个窗口,完全不影响其他窗口或任何 session
* 关闭所有窗口,应用进入"纯托盘模式",继续在后台运行
* 应用退出由用户主动从托盘触发,不和窗口生命周期绑定
* 所有窗口平等,不存在"主窗口"概念

> **Linux 平台例外(v1.6,ADR-013)**:此条对 Linux 不完全成立。GNOME 自 3.x 起官方移除 system tray,Ceteris 在 Linux 上不再做"沉托盘"行为(`lifecycleModel: 'no-persistence'`),关闭最后一个窗口 = 应用退出 = session 全销毁。配套阻塞 modal 在"最后一个窗口 + 仍有非 exited session"时弹出二次确认,作为无托盘环境的唯一 UX 妥协。Windows(`tray-resident`)和 macOS(`dock-resident`,Electron darwin 默认行为)保持原行为不变。"窗口零成本开关"在非最后窗口 / 全 exited session 关闭时三平台一致,只有"最后一个非空窗口关闭"在 Linux 上需要确认。详见 ADR-013 与第 12 章 `lifecycleModel`。

## 3. 目标用户

### 主要用户

* **Windows 平台的开发者**,日常工作中需要并发运行多个长时间命令行任务
* **同时运行多个 AI coding agent**(Claude Code、Codex、OpenCode 等)的开发者
* **不愿意学习 tmux / zsh / dotfiles 的用户** —— 他们需要工具开箱即用,而不是花一周配置环境
* **跨多个不相关项目工作的用户** —— 路径不一定是 git 仓库,可能是脚本目录、日志路径、网络盘等

### 典型场景

* RTL/EDA 工程师在多个 run 目录之间跳转,跑综合、仿真、回归测试
* 全栈开发者在前端项目 + 后端项目 + 脚本目录之间切换
* 同时让 5 个 agent 在 5 个不同项目里干活,不希望忘记任何一个的状态
* 跑长时间编译/部署/AI 任务,不希望因为关错窗口前功尽弃

### 非目标用户

* 重度 tmux / zsh 用户(他们已有满意工作流,Ceteris 不强迫他们改变)
* 团队协作场景中需要"项目级 session 共享"的用户(请用 Nimbalyst 等)
* 远程服务器管理为主的用户(请用 Windows Terminal + SSH 或专用 SSH 客户端)

## 4. 核心心智模型

### 三个一等公民,一种临时实体

Ceteris 的世界由四种实体构成:

```
应用(守护进程 + 托盘)—— 单例,长期运行,用户从托盘控制其生死
  │
  ├── Path(路径)—— 永久,用户管理,数据持久化
  │     │
  │     └── Session 1(会话)—— 临时,运行时产生,完成即销毁
  │     └── Session 2
  │
  └── Window(窗口)—— 临时观察工具,任意开关,彼此平等
```

**关键关系**:
* 应用持有 Path 数据和所有 Session
* Session 归属于 Path(由 cwd 决定)
* Window 是观察 Path 和 Session 的临时窗口,**不持有数据**
* 关闭 Window 不影响 Path,不影响 Session,不影响应用

### Path 的三种状态(由状态机自动管理)

```
[最近 Recent]
  ↑↓ (用户主动加入/移除收藏)
[收藏 Bookmarked]
  ↑↓ (有终端在跑/全部关闭)
[临时 Temporary]
```

**精确定义**:

| 分类 | 定义 | 是否自动 |
|------|------|---------|
| **收藏** | 用户主动加入的路径,永久保留 | 用户主动 |
| **临时** | 当前有终端在跑、且不在收藏区的路径 | 完全自动 |
| **最近** | 历史上开过终端、当前不在收藏也不在临时的路径 | 完全自动 |

**流转规则**:
* 在某路径新建终端 → 路径进入"临时"(若不在收藏)
* "临时"路径的最后一个终端关闭 → 路径离开"临时",进入"最近"
* "最近"或"临时"路径被用户加入收藏 → 进入"收藏",离开原分类
* "收藏"路径被用户移除收藏 → 回到"最近"(若有历史)或消失

**容量**:
* 收藏:无限
* 临时:无限(由当前活跃 session 数量决定,自然有限)
* 最近:最多 30 个,按最近活动时间排序,超出自动淘汰最旧的

### Session 的生命周期

```
[创建] → [活跃] ↔ [空闲] / [等待输入] → [已退出] → [销毁]
                                              ↑
                                       用户主动右键关闭 / 应用退出
                                       (无时限自动过期)
```

* **创建**:用户从某路径新建终端,守护进程启动 PTY 进程
* **活跃**:PTY 最近有字节输出
* **空闲**:PTY 一段时间无输出,但进程仍在
* **等待输入**:通过 OSC 1337 命令完成事件检测,处于 prompt 状态(V1.1)
* **已退出**:进程已结束(正常或异常),session 灯显灰色 ⚫,scrollback 仍可见;**不可重启**;无时限自动过期
* **销毁**:用户主动右键"关闭"、或应用完全退出时(批量销毁)

**核心承诺**:从 [创建] 到 [销毁] 的整个过程**与任何窗口的开关无关**。即使关闭所有窗口,守护进程依然管理这些 session。

**已退出 session 的语义**:像传统终端"crashed but tab still open"的体验。用户看到 ⚫ 灯 + 完整退出前的 scrollback;选项卡有右键"关闭"。**没有重启功能**,如果用户想"再跑一次",在同一 path 新建一个 session 即可。详见 ADR-008。

### Window 与 Session 的关系

```
N 个 Window(窗口,N ≥ 0)<──── 任意多对一/一对多 ────> M 个 Session(会话)
                                                            在守护进程内
                                                            持续运行
```

**核心约束 1:任一 Session 同一时刻只有 0 或 1 个 Owner Window**

* Owner Window 持有该 session 的输入/输出渲染权
* 非 Owner 窗口在自己的 UI 中**只能看到 session 存在**(灰显标签),不能直接显示其内容
* 用户在非 Owner 窗口点击灰显标签 → 系统聚焦真正的 Owner 窗口
* Session 可以无 Owner(所有窗口都关了,或最后一个窗口主动释放)

**核心约束 2:N 可以是 0**

应用启动后,可以保持 0 个窗口,只有托盘和守护进程运行。任何时候用户从托盘可以新开窗口。

**优雅之处**:这两个约束彻底消除了"多窗口同步同一 session"的所有复杂度,同时让窗口的开关变成纯粹的"观察方式选择",不绑定任何业务逻辑。

### 应用生命周期

```
[启动] → [运行(0~N 窗口)] → [完全退出]
              ↑↓
         窗口数量随时变化
         不影响应用本身
```

**应用何时退出**:
1. 用户从托盘菜单选"完全退出 Ceteris"
2. 系统关机/重启
3. 应用崩溃

**关闭窗口绝不等于关闭应用。**

## 5. 功能规格

### 5.1 必做(MVP V1)

#### 5.1.1 路径管理
* 添加收藏路径(通过文件夹选择器或拖拽 Explorer 文件夹)
* 移除收藏路径
* 重命名收藏路径(自定义显示名)
* 收藏路径排序(拖拽改变顺序)
* 临时路径自动出现/消失
* 最近路径自动记录,容量上限 30
* 用户右键最近路径可"加入收藏"或"从最近移除"

#### 5.1.2 Session 管理
* 在任一路径新建终端(默认 shell 或选择启动模板)
* 关闭终端:调用 `node-pty` 的 `kill()`,Windows ConPTY 立即终止子进程(无 SIGTERM/grace 周期 — 这是 ConPTY 模型决定的,不是软件设计选择)
* 已退出 session 保留在 UI 上(灯显灰色),用户可右键"关闭"销毁;**不可重启**
* 列出所有 session,按路径分组
* 状态指示:活跃 / 空闲 / 已退出(MVP 第一版只这三种)
* **session 与 path 的归属**:session 创建时记录的 path **永久绑定**,生命周期内不变。session 内 cwd 变化(cd 等)不会让 session 在 UI 上换 path,而是在该 session 的标签上显示 ⚠️ 提示真实 cwd(详见 ADR-008)

#### 5.1.3 启动模板
* 内置:Shell(系统默认)、Claude Code、Codex、OpenCode
* 用户自定义模板(命令、参数、环境变量、退出后行为)
* 每个收藏路径可设置"默认模板"(双击直接启动,跳过模板选择)

#### 5.1.4 终端体验
* xterm.js 渲染,支持 ANSI 颜色、Unicode 11、URL 自动识别可点击
* 终端搜索(Ctrl+F):弹出搜索栏,显示 `current/matches` 命中数;Enter 跳下一个 / Shift+Enter 上一个 / Esc 关闭。Ctrl+F、Esc 通过 `term.attachCustomKeyEventHandler` 在 xterm 把它们转成 PTY 字节流之前拦截,避免把 ^F / 0x1B 误送到 shell
* 复制(选中即可,可在设置关)、粘贴(右键 → 弹菜单 / 直接粘贴,设置可选)
* **多行粘贴确认**:剪贴板内容含换行(`\n`)时弹原生 `confirm`,显示行数 + 200 字预览;用户确认后再写入 PTY,避免误把脚本喂给 shell 立即执行
* 字体可配置 — 终端字体下拉枚举系统已安装等宽字体(走 `window.queryLocalFonts()`,主进程已自动放行 `local-fonts` 权限),并在顶部置顶推荐字体(Cascadia Mono / JetBrains Mono / Consolas / 霞鹜文楷 Mono 等);未装的推荐字体仍显示并标注"(未装)";不在推荐里的系统字体按字母升序展示;额外提供"自定义"输入框直接写 CSS `font-family`
* 字号 / 行高 / UI 字体 / UI 缩放 均可配置(数值范围见 6.6.2)

#### 5.1.5 多窗口支持
* 任意时刻可开任意多个窗口(包括 0 个)
* 所有窗口完全平等,不存在"主窗口"概念
* 关闭任意窗口不影响应用、其他窗口或任何 session
* 关闭所有窗口 → 应用进入"纯托盘模式",可随时从托盘新开窗口
* 每个窗口独立维护:当前选中路径、当前选中 session、侧栏展开状态
* 全局共享:收藏数据、最近数据、所有 session 列表、临时分类、设置
* 窗口标签:Window 1 / Window 2 / ... 自动编号(运行时分配,不持久化)
* 灰显标签 → 点击聚焦 Owner 窗口
* Owner 切换:用户在非 Owner 窗口点击同路径下的灰显 session(可选,V1 优先级低)

#### 5.1.6 守护进程与持久化
* 守护进程 = Electron Main Process,生命周期独立于任何窗口
* 第一个 Ceteris 实例启动时拉起守护进程(单例锁保护,通过 `app.requestSingleInstanceLock()`)
* 第二次启动 Ceteris.exe → 转发到已运行的实例,新开一个窗口
* 任何窗口关闭都不退出应用
* 用户从托盘"完全退出"→ 守护进程退出
* 数据持久化:收藏、最近、模板、设置 → JSON 文件,原子写

#### 5.1.7 系统托盘
* 常驻系统托盘,应用运行期间永不消失(除非"完全退出")
* 图标动态:有 session 在跑 / 全空闲(V1.1 加"有 session 等待用户")
* 单击托盘图标:聚焦最近活动的窗口;若无窗口,新开一个
* 右键菜单详细规格见 [6.5 系统托盘](#65-系统托盘)

#### 5.1.8 CWD 实时跟踪
* 通过 OSC 1337 序列追踪 session 内 cwd 变化
* **cwd 仅用于 UI 提示,不驱动 path 迁移**(ADR-008):session.currentCwd 与 session.pathId 对应的目录不一致时,该 session 的标签上显示 ⚠️ 图标 + tooltip 真实 cwd
* shell hook 注入透明完成,不污染用户 dotfiles(PowerShell 包装 prompt 函数;cmd.exe 嵌入 OSC 序列到 PROMPT 环境变量)
* 兜底策略:启动后首 5 秒内若未收到任何 OSC 1337,启动 5 秒间隔的进程 cwd 轮询(`PlatformAdapter.getProcessCwd`);收到首条 OSC 后立即关闭轮询。
  * **V1 实际状态**:`WindowsAdapter.getProcessCwd` 始终返回 `null` — 真正实现需要 `NtQueryInformationProcess` + 读 PEB,得引入 `ffi-napi` 原生包,违反 AGENTS.md 1.2 边界 2。SessionManager 内的轮询调度结构已就位,未来加原生绑定即生效。所以 V1 阶段 OSC 1337 hook 是 cwd 跟踪的**唯一**可靠路径。

#### 5.1.9 主题系统

### 6.2 左侧栏(资源管理器)

#### 6.2.1 顶部分类切换
三个分类标签:`[收藏] [临时] [最近]`
* 默认显示三个分类全部展开
* 用户可点击分类标题折叠/展开整个分类
* 分类标题旁显示该分类下的路径数量

#### 6.2.2 路径条目
每个路径条目显示:
* 折叠箭头(▶/▼)— 路径有终端时点击展开/收起终端列表
* 路径图标(收藏: `bookmark` / 临时: `schedule` / 最近: `history`)
* 路径显示名(用户自定义优先,否则路径最后一段)
* hover 时显示完整路径 tooltip
* 右侧显示该路径下活跃终端数量(若大于 0)
* 右键菜单(因分类而异):
  - 收藏:设置默认模板(V1 已实现);重命名 / 移除收藏 / 在 Explorer 中显示 / 复制路径(后续完善)

  - 无 owner → 本窗口接管并显示

* 收藏分类标题旁有 "+" 按钮

#### 6.2.4a 列表与石子两种视图
* 文件夹标题栏 "+" 左边的按钮在列表和石子之间切换,选择记在本机 localStorage(`ceteris.sidebar.folderLayout`),默认列表
* 石子视图:每个文件夹是一颗小石子,宽度随名字,像文字一样紧凑换行,不排成表格。每颗石子是同样的左右对称胶囊形。石子上是文件夹名和每个终端一个状态小圆点(颜色同终端行,超过 5 个写 +N)
* 正在显示的终端所在的那颗石子(或选中的文件夹)沿自己的轮廓描一圈主色边,石子视图里不用填充色。打开文件夹后,正在显示的终端行也描成一颗胶囊形石子的轮廓,不填色

* 打开某个文件夹时,从标签栏选中另一个文件夹的终端,侧栏跟着换到那个文件夹
* 右键菜单、重命名、标签、拖到终端区、运行中 / 等你处理筛选在两种视图里行为相同

#### 6.2.5 设置入口
* 侧栏底部固定显示一个齿轮图标 + "设置"文字

## 7. 交互规格

### 7.1 不做的交互

Ceteris 明确**不做**以下交互:

* **应用内功能键**:任何不在 §7.2.2 终端键位清单 / §7.2.1 鼠标交互之外的快捷键(无 Ctrl+T 新 tab、无 Ctrl+W 关 tab、无 Ctrl+Tab 切换 session、无 Alt+1..9 跳 tab、无菜单加速键、无任何 vim/emacs 风格)
* **全局快捷键**:不注册任何全局快捷键
* **命令输入框**:UI 中无任何"输入路径"或"输入命令"的文本框,所有路径必须通过文件夹选择器或拖拽

理由:这些交互假设用户是"愿意学习快捷键的命令行专家",而 Ceteris 的目标用户是"愿意用鼠标的普通开发者"。坚持鼠标优先工作流,产品才能保持自洽。

**§7.2.2 清单是唯一权威来源**:任何不在该清单内的键位必须透传给 PTY,renderer 层不得消费、不得弹 UI、不得改 state。任何 PR 加新键位必须先改 §7.2.2 并同步更新 `docs/键盘交互规范.md` 与 `src/renderer/terminal-keybindings.ts`。

### 7.2 必做的交互

#### 7.2.1 鼠标操作
* 点击侧栏路径:选中路径,在右侧显示该路径标签页 + 第一个终端(或加号)
* 点击侧栏路径展开箭头:展开/收起该路径下的终端列表
* 双击侧栏路径:在该路径用默认模板新建终端
* 点击侧栏终端条目:切换到该 session(本窗口)或聚焦 Owner 窗口
* 拖拽 Explorer 文件夹到侧栏收藏区:加入收藏
* 拖拽 Explorer 文件夹到终端区:在该路径新建终端
* 右键各处:上下文菜单

#### 7.2.2 终端内交互
* 选中文本即复制到剪贴板(类 Linux 风格,可在设置里关闭)
* 右键终端区:在设置中可选"弹菜单"(默认)或"直接粘贴"。弹菜单含:复制(选中时)/ 粘贴 / 清屏 / 搜索
* **多行粘贴确认**:剪贴板含换行时弹原生 `confirm`,显示行数 + 200 字预览;用户确认后才送入 PTY(防误粘脚本立即执行)。单行粘贴不打扰
* 滚轮:滚动 scrollback
* Ctrl+滚轮 / Cmd+滚轮:调整字号

##### 终端键位清单(唯一权威 — 此清单之外的所有键位透传 PTY)

| 功能 | Windows / Linux | macOS | 备注 |
|------|-----------------|-------|------|
| 复制 | `Ctrl+C`(有选区时)/ `Ctrl+Shift+C` / `Ctrl+Insert` | `Cmd+C` / `Ctrl+Shift+C` | 无选区时 `Ctrl+C` 透传 SIGINT |
| 粘贴 | `Ctrl+V` / `Ctrl+Shift+V` / `Shift+Insert` | `Cmd+V` / `Ctrl+Shift+V` | 所有路径走同一个 `handlePaste`(bracketed paste / 大粘贴警告 / ESC 检测) |
| 搜索 | `Ctrl+F` | `Cmd+F` | 唤出搜索栏,Enter=下一个,Shift+Enter=上一个,Esc=关 |
| 字号 | `Ctrl+Wheel` | `Cmd+Wheel` | 范围 8-24,本地立即生效,跨窗口 100ms debounce 广播 |
| 关搜索栏 | `Esc`(仅搜索栏可见时) | `Esc`(同) | 其他时刻 Esc 透传给 PTY(vim 等需要) |

**实现不变式**:
1. 上述键位通过 `term.attachCustomKeyEventHandler` + capture-phase `paste` listener 拦截,在 xterm 把它们转成 PTY 字节 / 让 native paste 进 PTY 之前接管
2. IME composition 期间(`isComposing` 或 `keyCode===229`)所有键位透传,renderer 不消费 — 避免打断中文 / 日文 / 韩文 IME 状态机
3. Esc 优先级走 `UiOverlayStack`:栈顶 overlay 吃 Esc,无 overlay 时透传给 PTY
4. 复制三套(`Ctrl+C 有选区` / `Ctrl+Shift+C` / `Ctrl+Insert`)统一 `copyAndClearSelection` — 否则下次 `Ctrl+C` 因残留选区无法发 SIGINT(CPB-C3)
5. session 切换 scrollback replay 期间 terminal-host `visibility:hidden + inert`,replay 完才 reveal — 按键不会进错位 focus(SCROLL-1)
6. 任何 PR 新增 / 改 / 删键位必须同时改:本节清单 + `docs/键盘交互规范.md` + `src/renderer/terminal-keybindings.ts` + 设置页快捷键速查卡片

### 7.3 拖拽行为

| 拖拽源 | 拖拽目标 | 行为 |
|--------|---------|------|
| Explorer 文件夹 | 侧栏收藏区 | 加入收藏 |
| Explorer 文件夹 | 终端区 / 加号区 | 在该路径新建终端(默认模板) |
| 侧栏路径条目 | 收藏分类内 | 改变收藏顺序 |
| 标签页 | 标签栏内 | 改变顺序(V1.2) |
| 标签页 | 窗口外 | 拆分到新窗口(V1.2) |

### 7.4 关闭与退出的精确语义

这是 Ceteris 与传统应用最大的不同之一,必须精确定义:

#### 7.4.1 关闭单个窗口
* 触发方式:点窗口右上角 × / Alt+F4 / 系统菜单关闭 / 托盘菜单"关闭所有窗口"中之一
* 行为:
  1. 该窗口立即消失
  2. 它持有的所有 session 的 `owner_window_id` 变为 `null`
  3. 那些 session 在守护进程中继续运行
  4. 其他窗口完全不受影响
  5. 应用继续运行
  6. **绝不弹任何确认对话框**

#### 7.4.2 关闭所有窗口
* 等价于逐个关闭每个窗口
* 关掉最后一个后,应用进入"纯托盘模式":
  - 没有任何窗口可见
  - 托盘图标继续显示
  - 守护进程继续管理 session
  - 用户从托盘可随时新开窗口
* **不弹任何确认**

#### 7.4.3 完全退出应用
* 触发方式:仅托盘菜单"完全退出 Ceteris"
* 行为:
  1. 若有 session 在跑且"完全退出前确认"开启 → 弹确认对话框
  2. 用户确认 → 给所有 PTY 发 SIGTERM,等待 5 秒
  3. 强制 kill 仍未退出的 PTY
  4. 持久化所有数据
  5. 守护进程退出
  6. 托盘图标消失
  7. 应用进程结束

#### 7.4.4 系统级关机/重启
* Windows 发送系统关机消息时,守护进程响应:
  1. 持久化数据
  2. 给所有 PTY 发 SIGTERM
  3. 退出
* 不阻止系统关机

              ┌──────────────────────┐

              │  - 创建托盘图标     │

                         │ 根据"启动时行为"设置
              ┌──────────┴──────────┐
              ↓                     ↓
    ┌──────────────────┐   ┌──────────────────┐
    │ 运行中(有窗口)│   │ 运行中(纯托盘)│
    │ Running w/ Win   │   │ Running Tray Only│
    └────────┬─────────┘   └────────┬─────────┘

             │  ←── 关闭最后一个窗口  │

                        │ 用户从托盘"完全退出"

              ┌──────────────────────┐
              │  退出中 Exiting     │
              │  - SIGTERM 所有 PTY │
              │  - 持久化数据       │
              │  - 托盘图标消失     │

              ┌──────────────────────┐
              │  未运行 NotRunning  │
              └──────────────────────┘
```

**注意**:
* "运行中"两个子状态可以反复切换,不影响应用本身
* 用户可以通过启动 Ceteris.exe 第二次来"新开窗口"(单例锁会转发给已运行的实例)

### 8.2 Path 状态机

```
            ┌──────────────────────────────────┐
            │         (用户主动加入收藏)       │
            ↓                                  │
       ┌────────┐  (有终端在跑)         ┌────────┐
       │ 最近   │ ────────────────────> │ 临时   │
       │Recent  │                       │Temp    │
       │        │ <──────────────────── │        │
       └────────┘  (最后一个终端关闭)    └────────┘
            ↑                                  ↑
            │         (用户主动加入收藏)       │
            │                                  │
            │  ┌────────┐                     │
            └─ │ 收藏   │ ←───────────────────┘
   (移除收藏) │Bookmark│  (用户主动加入收藏)
              │   ed   │
              └────────┘
```

**注意**:
* 收藏路径即使没有终端在跑也不会进入临时(收藏优先级高)
* 收藏路径有终端在跑时,仍只显示在收藏分类(不重复显示)
* 路径首次出现(从未开过终端、从未被收藏)只能通过"加入收藏"或"在此新建终端"两种方式

### 8.3 Session 状态机

```
                      ┌─────────────┐
                      │  Created    │ (PTY 启动)
                      └──────┬──────┘
                             │ (持续接收 PTY 字节流)
                             ↓
        ┌───────────┐  有输出 ┌──────────┐  无输出  ┌──────────┐
        │ Idle      │ ←────── │ Active   │ ──────→ │ Idle     │
        │ (空闲)    │         │ (活跃)   │ N秒     │          │
        └─────┬─────┘         └──────────┘         └─────┬────┘
              │  (PTY 进程退出)                           │
              ↓                                           ↓
              └────────────────┬─────────────────────────┘
                               ↓
                      ┌─────────────────┐
                      │  Exited         │ (灯显灰色 ⚫,无时限保留)
                      │  (已退出)       │ scrollback 完整保留
                      └─────────┬───────┘
                                │ (用户右键"关闭" / 应用完全退出)
                                ↓
                          ┌─────────┐
                          │Destroyed│
                          └─────────┘
```

**Active / Idle 阈值**:
* Active → Idle:无字节输出超过 2 秒(可在设置调整)
* Idle → Active:有任何字节输出

**Exited 的特性**:
* 进入即"挂起",**不再消耗任何资源**(PTY 句柄已释放,无定时器)
* `exitCode` 字段记录进程退出码;`scrollback` 仍持有
* **不能从 Exited 回到 Active**(无重启路径)。用户想"再跑一次" → 在同一 path 新建一个 session
* 销毁来源:用户主动右键"关闭" / 应用完全退出时批量销毁 / 收进收纳盒(ADR-036)

**收纳(ADR-036)**:Idle 或 Exited 的 session 闲置超过设置的时长(或用户右键"收进收纳盒")→ 直接 Destroyed,`reason = 'shelved'`;它的名字、文件夹、模板和 agent 会话 id 留在 `shelf.json`。从收纳盒"恢复"不是状态回退,是在同一 path 新建一个 session,Claude Code / Codex 带上 `--resume` / `resume`。

### 8.4 Window 与 Session 的所有权状态

每个 Session 有一个 `owner_window_id` 字段,可能值:
* 某个 Window 的 ID — 该 Window 当前持有此 session
* `null` — 此 session 当前无 owner

**所有权转移规则**:
* Window A 持有 Session X,用户在 Window A 切换到 Session Y → A 释放 X(变 null),A 持有 Y
* Window A 持有 Session X,Window A 关闭 → X 的 owner 变 null
* 用户在 Window B 点击 X(此时 X 的 owner 是 A)→ 守护进程聚焦 A,所有权不变
* Session X 无 owner,用户在 Window B 点击它 → B 接管,X.owner = B
* 应用进入"纯托盘模式"(无窗口)→ 所有 session 的 owner 都是 null

## 9. 技术架构

### 9.1 总体架构

```
┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
│  UI Window 1     │  │  UI Window 2     │  │  UI Window N     │

         └──────────┬──────────┴─────────────────────┘

         │  │ Settings Manager       │  │
         │  │  (设置数据 + 广播)     │  │
         │  └────────────────────────┘  │
         │  ┌────────────────────────┐  │

         │  └────────────────────────┘  │
         │  ┌────────────────────────┐  │
         │  │ Persistence            │  │
         │  │  (JSON 文件 I/O)       │  │
         │  └────────────────────────┘  │
         │  ┌────────────────────────┐  │
         │  │ Tray                   │  │
         │  └────────────────────────┘  │
         │  ┌────────────────────────┐  │
         │  │ Platform Adapter       │  │
         │  │  (Windows-only V1)     │  │
         │  └────────────────────────┘  │
         └──────────────────────────────┘
                    ↓
         ┌──────────────────────────────┐
         │  System APIs                 │
         │  ├─ Tray (Electron)          │

**关键说明**:
* 守护进程 = Electron Main Process,不是独立的可执行文件
* 每个 UI Window = 一个 BrowserWindow + 一个 Renderer 进程
* Main 与 Renderer 之间用 Electron 标准 IPC(`ipcMain` / `ipcRenderer`)
* 多窗口共享同一个 Main 进程,自然共享所有数据
* Window 数量可以是 0:此时 Main 仍在运行,只有托盘可见

### 9.2 进程职责划分

#### 9.2.1 Main Process(守护进程)
* 创建和管理所有 PTY(node-pty)
* 维护 session 状态、scrollback buffer
* 维护 path 数据(收藏/临时/最近)
* 维护 window 列表与 owner 关系
* 维护设置数据 + 广播变更
* 持久化数据(JSON I/O)
* 系统托盘
* 系统 API 调用(注册表、cwd 查询、单实例锁)
* 单一可信数据源
* **生命周期独立于任何窗口**:监听 `app.on('window-all-closed')` 但不调用 `app.quit()`

#### 9.2.2 Renderer Process(每个窗口一个)
* 渲染 React UI(侧栏、标签页、终端区、设置 UI)
* 维护**本窗口独立的视图状态**:
  - 当前选中的路径(选中状态)
  - 当前选中的 session(显示哪一个)
  - 侧栏分类的展开/折叠状态
  - 路径展开状态
  - 当前是否在设置视图
* 处理用户交互,通过 IPC 把意图发给 Main
* 接收 Main 推送的 PTY 字节流,送给 xterm.js 渲染
* 接收 Main 推送的设置变更,实时应用

**关键原则**:Renderer 不存储任何全局状态。所有"全局可见"的数据都从 Main 拉取或订阅。

### 9.3 数据流示例

#### 用户在路径 A 新建一个 Claude Code 终端

```
1. Renderer (Window 1):用户点击 "+" 按钮,选 Claude Code 模板
2. Renderer → Main:IPC 调用 createSession({ pathId: 'path-a', templateId: 'claude-code' })
3. Main:
   a. 启动 node-pty,cwd = path A 的实际目录,command = "claude"
   b. 注入 OSC 1337 hook(根据所选 shell)
   c. 创建 Session 对象,owner_window_id = window1.id
   d. 把 Session 添加到 path A 的 sessions 列表
   e. 如果 path A 不在收藏,加入临时分类
4. Main → 所有 Renderer:广播 path 树更新事件
5. Main → Window 1:推送该 session 的字节流(只推给 owner)
6. Window 1 Renderer:收到字节流,送给对应的 xterm.js 实例
```

#### 用户在 Window 2 点击 Window 1 持有的 session

```
1. Window 2 Renderer:用户点击灰显 session
2. Renderer → Main:IPC focusSessionWindow({ sessionId })
3. Main:查 session.owner_window_id == window1.id
4. Main → Window 1:命令该窗口 focus()
5. Window 1 浮到前台,选中那个 session 的标签
```

#### Session 内 cwd 变化(自 v1.2 起,**不再驱动 path 迁移**)

```
1. PTY 内的 shell 执行用户的 `cd /new/path`
2. PTY 输出 OSC 1337 序列:\x1b]1337;CurrentDir=/new/path\x07
3. Main 解析字节流时识别到 OSC 1337,提取序列后透明转发剩余字节给 owner
4. Main 更新 session.currentCwd(session.pathId 不变)
5. Main → 所有 Renderer:广播 sessionStateChanged({ id, currentCwd })
6. Renderer 比较 session.currentCwd 与 session 所属 path 的 path 字段:
   - 一致 → 标签正常显示
   - 不一致 → 标签旁显示 ⚠️ 图标,tooltip 显示真实 cwd
7. **path 状态机不被触动**(session.pathId 永久绑定,见 ADR-008)
```

#### 用户关闭 Window 2(不影响其他)

```
1. 用户点击 Window 2 的 ×
2. Electron 触发 'close' 事件
3. Main 监听到 → 找到 Window 2 持有的所有 sessions
4. 对每个 session:owner_window_id 改为 null
5. Window 2 真正销毁(Renderer 进程退出)
6. Main → 所有剩余 Renderer:广播 window-list-updated + sessions-state-updated
7. Main 检查窗口数量:
   - 还有窗口 → 继续运行
   - 没有窗口 → 进入"纯托盘模式",不退出应用
```

#### 用户在设置 → 数据 → 导入归档(自 v1.3 起,**in-memory replace**,不重启应用)

```
1. Renderer:用户点"导入…"按钮
2. Renderer → Main:IPC SETTINGS_IMPORT
3. Main:dialog.showOpenDialog 选 JSON 文件
4. Main:fs.readFile + JSON.parse + validateArchive(format / version 校验)
5. Main:dialog.showMessageBox 二次确认("整体覆盖现有配置,继续?")
6. 用户确认 → applyArchiveInMemory:
   a. settingsManager.replaceAll(archive.settings)   // deep-merge + validate + emit
   b. templatesManager.replaceAll(archive.templates) // mergeBuiltins + persist + emit
   c. pathManager.replaceAll(archive.bookmarks/recent) // persist + emit
   d. await Promise.all([flush, flush, flush])      // 等磁盘 debounce 落盘
7. Main → 所有 Renderer:广播 settings:changed / templates:updated /
                          path:tree-updated / bookmarks:updated
8. 各窗口 Renderer:reducer 应用变更,UI 立即刷新
9. 运行中的 PTY session 不被打扰(导入只换数据,不动 session 树)
```

**为什么不再 `app.relaunch + app.quit`**:dev 模式下 `app.relaunch` 与 Vite HMR daemon 协作不稳,新进程拉起后 renderer URL 失效,用户看到"导入后无法正常渲染"。In-memory 路径在 dev / 打包模式都自然工作,且符合"窗口零成本开关 / session 与 UI 解耦"哲学。详见 ADR-009。

### 9.4 IPC 协议

完整 IPC 协议(命令通道、事件通道、信封 schema、错误码、字节流编码)已在 [`docs/ipc-protocol.md`](./ipc-protocol.md) 单独定稿,版本与 `src/shared/protocol.ts` 中的常量同源。

主要分组:
* **命令通道**(Renderer → Main,`ipcRenderer.invoke` + `ipcMain.handle`):
  - app:get-protocol-version / get-snapshot / quit
  - window:create / close-self / close-all / focus
  - session:create / close / claim / release / focus-owner / send-input / resize / get-scrollback
  - bookmark:add / remove / rename / reorder / set-default-template / pick-folder
  - path:remove-from-recent
  - settings:get / update / reset / list-shells / get-auto-start / export / import
  - template:add / update / delete / set-default
  - system:show-in-explorer / open-data-dir / open-logs-dir / open-external
* **事件通道**(Main → Renderer,广播):
  - path:tree-updated / bookmarks:updated
  - session:created / owner-changed / state-changed / exited / destroyed / output
  - templates:updated
  - window:list-updated / focus-requested
  - settings:changed
  - app:state-changed

**信封**:每条命令带 `{ windowId, requestId, payload }`,每条事件带 `{ eventId, timestamp, payload }`(见 ipc-protocol.md 第 2 章)。
**安全**:`open-external` 仅放行 `http(s)` / `mailto`;`add-bookmark` 强制目录存在校验。

### 10.2 关键决策记录

#### ADR-001:为什么选 Electron 不选 Tauri
* node-pty 是 Microsoft 官方维护的 Node 模块,VS Code 在用
* xterm.js 是 JavaScript 库,在 Electron 的 Chromium 上验证最充分
* 多窗口 + 共享主进程的架构与 Electron 模型完全对齐
* 开发迭代速度(JS 热重载 vs Rust 编译)对单人项目重要
* 包大小、启动速度等 Tauri 优势在本场景下不重要(常驻应用,启动一次)
* 学习曲线:作者熟悉 JS / TS,不熟悉 Rust

#### ADR-002:为什么 IPC 用 Electron 原生而不是独立守护进程 + Named Pipe
* Electron Main Process 本身就是 Node.js 守护进程,无需再开一层
* Renderer 与 Main 之间用 Electron IPC 极快
* 简化部署:一个 .exe 即所有
* 缺点:守护进程不能在 UI 全部退出后独立运行 — 通过"托盘常驻"+"窗口可独立关闭"+"`window-all-closed` 不退出"解决

#### ADR-003:为什么用 OSC 1337 而非进程 cwd 查询作为主方案
* OSC 1337 是事件驱动,毫秒级响应,远胜轮询
* iTerm2、VS Code、Wave、Warp 都用此机制,生态成熟
* 进程 cwd 查询(NtQueryInformationProcess)作为兜底:每 5 秒一次,**仅在启动后首 5 秒未收到任何 OSC 1337 时才启动**(收到首条 OSC 后立即关闭轮询,大多数 session 永远不消耗轮询开销)
* **(v1.2 调整)**:OSC 1337 不再驱动 path 迁移,仅用于在标签上提示真实 cwd。详见 ADR-008

#### ADR-004:为什么 session 用完即弃,不维护跨会话上下文
* AI agent 上下文消耗 token,跨 session 累积消耗指数膨胀
* 真正需要持久化的知识应进 git / 文档 / CLAUDE.md
* agent 自己有 `claude -c` 等机制处理"continue 上次"
* 简化数据模型,降低实现复杂度
* 2026-11-10 起,ADR-039 放宽这一条:标签在重启之间保留(进程不保留),对话由 agent 自己按 id 续上,Ceteris 仍不保存屏幕和上下文。

#### ADR-005:为什么一个 session 同时只有一个 owner window
* 多 owner = 多 client 字节流广播 + scrollback 同步 + 输入冲突协调,复杂度 5x
* "关 UI 不死"的核心价值不需要"多窗口同时显示同一 session"
* "多屏幕同时看"的场景由屏幕共享 / 投屏解决,不应是终端工具的责任
* 协议层留出多 owner 扩展点(owner 字段设计为 list),但 UI/服务端实现都按单 owner

#### ADR-006:为什么所有窗口完全平等,无主窗口概念
* 主窗口模型继承自 Win32 时代,与"应用 = 数据 + 多个观察窗"的现代心智不符
* 主窗口模型导致用户必须思考"我能不能关这个窗口"的决策疲劳
* 平等模型下用户的心智简化为"窗口是观察工具,关掉再开就好"
* 实现上反而更简单:无需为"主窗口"加特殊保护逻辑
* 用户可以零顾虑地新建/关闭窗口,匹配多屏多场景使用

#### ADR-007:为什么设置即改即生效,无保存按钮
* 用户改完不知道要点保存的体验糟糕
* 主题、字体等"调整型"设置必须实时反映才能边调边看
* 配置存盘代价低(JSON < 10KB),debounced 写入即可
* 仅"重置所有设置"等破坏性操作需要二次确认

#### ADR-008:为什么 path 与 cwd 解耦,且砍掉 5 分钟墓地+重启(v1.2 启动 CP-3 前确立)

**变更内容**:
1. session.pathId 在创建时确定,**生命周期内永远不变**;session 内 cd 不再让 session 在 UI 上迁移 path 分类
2. cwd 变化仅触发标签上的 ⚠️ 提示(currentCwd ≠ originalPath 时),不动 path 树
3. 砍掉 Tombstoned 的"5 分钟自动过期"和"用户重启" — 进程退出后 session 进入 Exited 灯显态,无时限保留,直到用户主动关闭

**变更理由**:

**关于 path 与 cwd 解耦**:
* 原方案让 session 跟随 cwd 在侧栏分类间"跳",用户心智上很费力 — "我刚在 ~/projects/auth 起的 claude,怎么突然出现在 ~/Downloads 了?"
* path 是"工作位置"的稳定索引,session 是该位置上的临时活动,cd 只是 session 内部的工具行为,不应该污染上层组织
* 新规则更稳:**"我在 path X 下打开的终端,就属于 path X,无论里面发生什么"**
* 实现复杂度大幅降低 — PathManager 不再需要"detach 旧 path / attach 新 path / 重新计算分类",cwd 跟踪只是 UI 装饰
* OSC 1337 仍然主推,因为我们仍需要知道真实 cwd(给 ⚠️ 提示、未来"在 Explorer 中显示"功能、可能的"在当前 cwd 新建终端"等)

**关于砍墓地**:
* 5 分钟墓地的初衷是让用户撤回误操作 / 看 claude 退出后的最终响应,但实测 5 分钟既太短(用户离开吃饭就过了)又太长(占用心智的标签灰显几分钟很烦)
* "重启"功能在 path 与 cwd 解耦后语义模糊 — 用什么 cwd 重启?用 originalCwd 用户体验和"新建一个"几乎一样
* 砍掉后:进程退出后 session 进入 Exited 状态,scrollback 完整保留,**无时限**等待用户;用户想看就看,看完右键关闭;想再跑一次就在同一 path 新建一个
* 这其实是更接近"传统终端 + 标签持久"的体验:tab 不会"自己消失"
* 数据模型更简单:删 `tombstonedAt` / `sessionTombstoneMinutes`;state 枚举是 `'active' | 'idle' | 'exited'` 三态终态可观察

#### ADR-009:为什么设置导入改 in-memory replace,移除 followSystemTheme(v1.3,CP-4 勘误)

**变更内容**:

1. **移除 `appearance.followSystemTheme`** 字段 + UI 开关 + main 端 `nativeTheme.on('updated')` wiring。
2. **设置导入路径重写** — 由"`fs.writeFile` 4 个 JSON + `app.relaunch + app.quit`"改为"各 Manager 的 `replaceAll()` + emit 事件 → 所有窗口实时刷新",**不再重启应用**。
3. **CSP 通过 `webRequest.onHeadersReceived` 在 main 进程注入**(dev 含 `unsafe-eval` 给 React Refresh,生产严格);不再用 index.html 的 meta CSP(避免 Vite HMR 与 meta CSP 冲突)。dev 模式同时 `process.env.ELECTRON_DISABLE_SECURITY_WARNINGS = 'true'`(unsafe-eval 是有意为之,Electron 仍会在控制台 warn,这是它的硬编码检查;打包后该模块不加载,无影响)。
4. **`window.queryLocalFonts()` 启用** — main 端 `setPermissionRequestHandler` 自动放行 `local-fonts` + `clipboard-read` 权限;字体下拉用真实安装列表而非写死白名单。
5. **状态机微调** — `SessionManager.createSession` 末尾立即 `scheduleIdleCheck()`,防止首波 PTY 数据是纯 OSC(passthrough 空)时永远卡在 `active`。

**变更理由**:

* **followSystemTheme 不可靠**:Windows 上 `nativeTheme.shouldUseDarkColors` 在多用户 / 远程会话 / 系统未配置颜色模式的机器上经常返回错误值,导致主题"自己跳",反而是 bug 来源。7 套主题让用户主动选,是更确定的体验。
* **`app.relaunch` 在 dev 失效**:electron-vite 的 dev daemon 拉起 main 进程后,`app.relaunch` 触发的二次启动与 Vite dev server 之间会失联,renderer URL 不可用,用户看到"导入后无法正常渲染"。In-memory replace 在 dev 与打包都自然工作。
* **In-memory replace 也更符合产品哲学**:导入是数据层面的事,运行中的 PTY session 不应被关 — 这与"窗口零成本开关 / session 与 UI 解耦"完全一致。
* **CSP via headers**:meta CSP 在 Vite dev 模式下与 HMR 注入的脚本互冲(`script-src 'self'` 会拒绝 Vite 内联);headers 路径让我们对 dev / prod 分别精准下发,避免双重 CSP 源冲突。
* **queryLocalFonts**:之前用 Canvas measureText probe 写死白名单是双输 — 既漏掉用户自己装的字体,又把未装的列出来。Local Font Access API 是 Chromium 原生方案,Electron 通过 permission handler 一键放行即可。

**实现要点**:
* 各 Manager 暴露 `replaceAll(input)` 方法(`SettingsManager` / `PathManager` / `TemplatesManager`),走的还是各自的"validate / merge / persist / emit"路径,与运行时 update 同源。
* `applyArchiveInMemory` 在 `ipc.ts` 顺序调用三个 `replaceAll` 后 `await Promise.all(flush)` 等磁盘 debounce 落盘。
* IPC 事件 `evt:settings:changed` / `evt:templates:updated` / `evt:path:tree-updated` / `evt:bookmarks:updated` 自然广播到所有窗口,reducer 合并即生效。

#### ADR-010:为什么自绘标题栏 + macOS / Windows 双布局(v1.4,Milestone 1)

**变更内容**(M1-A):
1. `BrowserWindow` 改为 `frame: false`,完全自绘标题栏(`WindowChrome.tsx`)。
2. 新增 `settings.appearance.windowStyle: 'windows' | 'macos'`,默认 `'windows'`。
3. Windows 布局:控制按钮在右侧(最小化 / 最大化-还原 / 关闭),Material Symbols 图标,方形热区。
4. macOS 布局:三色 traffic light 在左侧(红/黄/绿圆形),hover 显示内部符号 ×/−/⤢;标题居中。
5. 新增 IPC:`cmd:window:minimize` / `cmd:window:toggle-maximize` / `cmd:window:get-max-state`;事件 `evt:window:max-state-changed`。
6. `Menu.setApplicationMenu(null)` — 彻底禁默认菜单条(File/Edit/View),与 spec 7.1"不做应用内快捷键"一致。

**变更理由**:
* 原 OS 默认 frame 在 7 套主题下视觉断裂(尤其深色主题:Rose Pine base #191724 vs 系统白色标题栏)。daily driver 每天看 8 小时,这种割裂是反复的视觉摩擦。
* 用户对"标题栏风格"的偏好是真实存在的二分:习惯 Win 风格的人讨厌 macOS 按钮位置,反之亦然。强制一种是错配。
* macOS 风格不仅是按钮位置,整体 chrome 更紧凑(32px vs 36px),适合"低视觉噪声"的开发者偏好;Windows 风格按钮更大,符合 Fitts's Law 的 Win11 设计语言。
* 自绘后免去了 OS 主题切换时的"标题栏抖一下"问题。
* `Menu.setApplicationMenu(null)` 是必须的同步动作,否则 Alt 还能弹出隐藏的菜单条,与自绘标题栏叠加视觉混乱。

**风险/边界**:
* Windows 7/10 没有 Window Controls Overlay(`titleBarOverlay`),但我们走纯自绘按钮路径,所有版本都一致。
* 全屏 / 最大化时窗口外圆角通过 `[data-maximized="true"]` 取消(代码已挂)。
* macOS 真机 V1 不测试(`mac:` 配置只为社区贡献者占位),`windowStyle: 'macos'` 是 Windows 上的"视觉风格选项"而非"模拟 macOS 行为"。

#### ADR-011:Milestone 1 内部上线的其他工程决策(v1.4)

打包成一个 ADR 是因为这些决策都来自同一时间点的"准备日常使用"评估,各自单写过细。

* **窗口位置记忆走 settings 而非独立文件**(M1-G):`windowDefaults` 是单一组而非 per-windowId,因为 windowId 是 UUID 不复用,而且"窗口零成本开关"哲学下,记每个窗口的位置毫无意义。"最后关闭的窗口"作为下次默认就够了。多显示器越界检测在 `resolveInitialBounds`,外接屏拔了自动回退主屏居中。
* **持久化日志自建,不引入 electron-log**(M1-D):AGENTS.md 1.2 边界 2。日均日志量 < 5 MB,日切 + 7 天保留,Node 内建 `createWriteStream` 完全够。一旦真要做远程上报再考虑。
* **崩溃兜底是 `keep alive` 而非"重启自愈"**(M1-D):未捕获异常多半是边角 bug,损坏的状态在下次操作时各 Manager 会重新校验。直接退出会丢所有 PTY,远比"带轻微 inconsistent state 继续跑"代价大。
* **托盘动态图标只两态**(M1-H):active / default;spec 6.5.1 提及的"waiting-input"是 V1.1 的状态识别扩展,本期不做。
* **导出归档敏感凭据弹三选一,不内置 keyring**(M1-F):正经凭据存储是 V1.x+ 的事;现在让用户每次导出明确决定"含/不含 env",已经比"默认明文导出"安全很多。
* **启动期 grace 1.5s**(M1-I):比 RESIZE_QUIET_MS 长(500ms),因为 PowerShell banner + profile 加载在慢机上能跑 1+ 秒;太短会闪,太长会让"刚开就跑命令"的 session 状态点延迟变 active(但 idle timer 仍正常启,所以最坏情况是首 1.5s 状态点稳定显示 active 而非闪烁)。
* **Ctrl+滚轮调字号通过 settings.update**(M1-I):全局生效,所有窗口同步。不做"per-session 字号"(违反"session 廉价 / settings 全局"哲学)。
* **env 字段 blur 遮罩而非真 password input**(M1-I):textarea 不支持 type=password。CSS `filter: blur(4px)` 实现视觉遮罩,hover/focus 自动解除,既保护偷瞄又不影响日常编辑。
* **第三方 prompt(starship/OMP)兼容性**(P1-5)**推后到上线后验证**:暂时不在 M1 内修。PowerShell 在 `-Command` 之前自动加载 `$PROFILE`,我们的 `pwsh.ps1` 随后 wrap prompt(hook 不再自己 dot-source `$PROFILE`,否则 profile 会跑两次),理论上后注入的 OMP 会覆盖我们 → cwd 跟踪失效。日常验证发现失效再加 PSReadLine hook 路径(避免在装了 OMP 的开发者真机上才发现,从而进入 M2 勘误)。
* **`build/icon.ico` 离线生成**(M1-E):AGENTS.md 1.2 边界 2 不装 electron-icon-builder。SVG 源 + README 指引(在线工具/ImageMagick/PNG fallback),实际 .ico 由作者一次性生成放入,这是"零依赖 + 一次性手工"的合理折衷。

#### ADR-012:为什么 alpha 末改名 EasyTerm → Ceteris(v1.5)

**变更**:产品 alpha 阶段(CP-1 ~ Milestone 1)的开发代号 **EasyTerm** 在 v1.5 改为正式产品名 **Ceteris**。

**触点**:
- `package.json` `name` / `description` / `homepage`
- `electron-builder.yml` `appId` / `productName` / `nsis.shortcutName`
- 窗口标题、托盘 tooltip、托盘菜单文案、退出对话框、设置页"关于"、字符串中所有 brand 出现
- shell hook 内部标识符(`__easyterm_emit_cwd` → `__ceteris_emit_cwd`)与日志前缀
- 用户数据目录 `%APPDATA%\Ceteris\`(Electron 由 `productName` 自动派生)
- 归档格式 `ceteris-archive`(读侧仍接受 `easyterm-archive` 旧值)

**变更理由**:
- "EasyTerm" 是描述性的功能名(easy + terminal),没有产品感,不易在 GitHub / 工具市场上让人记住。
- "Ceteris" 是隐喻名:**码头 / 船坞**。多艘船(session)同泊;船关港不影响港湾本身(关窗不杀 session);船在港之间游弋(session 跨 path 切换);这套意象与产品哲学"path 是稳定的、session 是廉价的、UI 是临时的"高度同源。
- 名字软、容易记、4-6 字母、域名虽然主域被抢但 `.so` / `.sh` / `ceteristerm.com` 可注 — 改名时机在 alpha 末 / 正式上线前,代价最低。

**风险与缓解**:
- **现存用户数据**:Electron 由 `productName` 派生 `app.getPath('userData')`,改名后**数据目录从 `%APPDATA%\EasyTerm\` 切到 `%APPDATA%\Ceteris\`**,老数据会"看起来丢了"。**作者本人需在改名后启动新版前手动 copy 一次**(`Copy-Item -Recurse $env:APPDATA\EasyTerm\* $env:APPDATA\Ceteris\`)。M1-G 的 `windowDefaults` 也走这一步迁移。
- **归档格式**:读侧同时接受新旧两个 `format` 字段,所以旧 EasyTerm 导出的备份仍能在新 Ceteris 里导入。导出统一用新名。
- **历史文档**:`docs/checkpoints/`、cp2/cp3/cp4 勘误、各 milestone 工作记录 等历史档保留 EasyTerm 字样作为时间点快照(在它们的头部加一行简短迁移说明)。
- **shell hook 标识符**:`__easyterm_emit_cwd` 等是注入到用户 shell 进程的函数名;每个 session spawn 时重新注入,改名后立即生效,不影响"已在跑"的 session(它们的 hook 函数在用户 shell 里已加载,session 结束就消失)。

#### ADR-040:代码和数据文件可查看、编辑、高亮,保存后用本机 linter 检查(2026-11-11)

**背景**:开发者用 Ceteris 跑 agent 做经济学研究,文件树里大多是 R、Python、Julia、Stata、SQL / HiveQL 脚本和 csv。此前只有 txt、json、tex、md 能在终端旁打开,其余文件要切到别的编辑器才能看一眼。开发者要求这些文件也能查看、编辑,并且有 linter。

**决策**:

1. **一张表管类型**。`src/shared/code-files.ts` 按扩展名列出可编辑的类型、各自的语言、是否显示行号、是否折行、用哪个 linter。`file-tree.ts` 的文本类型从这张表生成,加一行就支持一个新扩展名。当前有:py、R、Rmd、qmd、jl、sql、hive、do、ado、m、mod(Dynare)、sas、gms、f、f90、cpp、yaml、yml、toml、ini、cfg、sh、ps1、csv、tsv、log、bib,以及原有的 txt、md、json、tex。扩展名允许带数字(f90、ps1)。
2. **编辑器换成 CodeMirror 6**。textarea 换成 CodeMirror(`@codemirror/state`、`view`、`commands`、`language`、`lint`、`legacy-modes` 和 `@lezer/highlight`,开发者 2026-11-11 批准)。高亮用 legacy-modes 里的 CodeMirror 5 模式,一个包覆盖全部语言;Stata 没有现成模式,自写 `src/shared/stata-mode.ts`。颜色全部取当前主题的 CSS 变量(关键字 `--color-accent-special`,字符串 `--color-success`,数字 `--color-warning`,注释 `--color-text-muted`),所有主题和用户主题自动适配。代码显示行号、不折行;txt、md 这类文字照旧折行、不显示行号。超过 2 MiB 的文件仍是分段只读的纯文本。
3. **按键只保留文本编辑本身**:光标移动和撤销 / 重做(textarea 原本就有),再加 Tab 缩进(先按 Esc 再按 Tab 可以移出编辑器)。不加 Ctrl+S、搜索面板、补全,13.2 的应用内快捷键禁令照旧。
4. **lint 只用用户自己装的工具,只在保存成功后跑**:ruff 查 Python,lintr 查 R、R Markdown 和 Quarto,sqlfluff 查 SQL 和 HiveQL。PATH 上有就直接用;ruff 和 sqlfluff 没装但有 `uvx` 时经 uvx 运行;Rscript 不在 PATH 时到 R 安装器的默认目录找(`PlatformAdapter.knownToolPaths`,因为 Windows 的 R 安装器不改 PATH)。都没有时,编辑器下方显示一行安装命令,不替用户安装。ruff 带 `--no-fix --no-cache`,既不改文件,也不在项目里留缓存目录。sqlfluff 从 stdin 读文本,所以 .hive 这种它不认识的扩展名也能查;没有写了 dialect 的 sqlfluff 配置时,.hive 用 hive,.sql 用 ansi。Julia、Stata、MATLAB 没有通用的命令行 linter,只高亮。
5. **问题的显示用方案 D**(开发者从四个方案里选的):有问题的地方画波浪线,悬停看说明;编辑器下方的面板按位置列出全部问题,点一行跳到那里,面板可以收起。没有问题时只剩一行"没有发现问题"。保存后用户若继续打字,波浪线随编辑移动,不会错位。
6. **Link 窗口**:`cmd:code:lint` 和保存一样转发给 Host,在文件所在的机器上跑。SSH 文件只读,不 lint。

**为什么不是别的方案**:
- 不内置 linter(比如用 Pyodide 跑 ruff、用 webR 跑 lintr):体积大,版本也和用户项目的配置对不上。用户自己的 ruff、lintr 会读项目里的配置。
- 不边打字边 lint:每次按键起一个进程太重,而且 Rscript 启动要一两秒。
- 不用 highlight.js 叠在 textarea 下面:光标和颜色很难对齐,波浪线也只能退化成列表。

**未做**:不做格式化、补全、跳转定义;Julia、Stata、MATLAB 没有 lint;R Markdown 和 Quarto 不分代码块高亮。

#### ADR-039:启动时把上次的标签开回来,agent 按 id 接上对话(2026-11-10)

**背景**:从 GitHub 下载安装新版本时,安装程序会结束 Ceteris,所有终端随之关掉;崩溃也一样(KI-004)。重新打开后标签全没了,用户要一个个重开,再在每个 agent 里手动 resume。开发者 2026-11-05 决定每次启动都恢复标签(不只崩溃后),2026-11-10 确认先做这一步,安装仍由用户自己点。

**决策**:

1. **持续保存,不靠退出时写**。安装程序通常直接结束进程,`before-quit` / `will-quit` 不一定跑。main 的 `SessionRestorer` 监听 session 的创建、销毁、退出、owner 和状态变化,1 秒防抖后把全部未退出的标签写进 `restore.json`;另每分钟写一次,带上 agent 报来的会话 id 和最新的活动时间。正常退出时先 `freeze()` 写最后一次再停止监听,随后的 `shutdown` 关掉所有 session 不会把文件清空。恢复进行中不写,半路崩溃不会丢掉还没开回来的标签。
2. **什么开回来**(`shared/session-restore.ts` 的 `restoreKind`):纯 shell 模板和内置 agent 模板直接开。自定义模板可能跑任何命令,SSH 可能要密码,管理员 Shell 要提权,这三类不在启动时自己跑,放进收纳盒(ADR-036,`reason = 'restore'`),点一下再开。模板已删除的跳过。已退出的标签不保存。
3. **按 id 续,不按文件夹猜**。Claude Code 和 Codex 只用会话 id(`--resume <id>` / `resume <id>`):ceteris-tabs 钩子报过的用它,没报过的在启动时按保存的文件夹和时间去 agent 的记录文件里找(复用 ADR-036 的 `agent-resume.ts`)。同一个 id 不会给两个标签,重复的当作没找到。找不到 id 就开新对话,不退回 `--continue`:同一文件夹常有几个标签,文件夹里也可能根本没有对话。其他内置 agent 没有 id 可查,只有该标签是这个文件夹里该 agent 的唯一一个,才用 ADR-037 的文件夹级参数。
4. **开之前先查 id 还在不在**(`agentSessionExists`)。Claude Code 要在启动目录对应的 `~/.claude/projects/<slug>/` 里有 `<id>.jsonl`,Codex 要在 `~/.codex/sessions/` 下有 `rollout-*-<id>.jsonl`;不在就开新对话。不能事后补救:agent 跑在 `-NoExit` 的 shell 里,`claude --resume` 失败只会退回 shell 提示符,标签不会退出,没有信号可等。ADR-037 的"8 秒内退出就不带参数重开"因此在 Windows 上触发不了,见 known-issues。
5. **窗口与名字**。上次窗口正在显示的标签开回来时归第一个窗口;有几个时取最后按过回车的那个。其他标签无 owner,在标签栏里等着。用户改过的名字和 agent 标签的标题保留,shell 的自动标题照常跟随;角色(协调者、Fintuner)恢复。不给开回来的 agent 发 "continue":退出是用户的决定,开回来的 agent 等用户说话。
6. **开关**:`settings.behavior.restoreTabsOnLaunch`,默认开。冒烟测试和简易模式不恢复;从资源管理器"在 Ceteris 打开"冷启动时照常恢复,但不占那个窗口。

**为什么不是别的方案**:
- 不只在退出时写:装新版本这个最主要的场景恰好不走正常退出。
- 不保存屏幕或 scrollback:对话在 agent 自己的文件里,按 id 续上就是完整的;保存屏幕既大又可能含敏感输出。
- 不用 `--continue` 作为默认:同一文件夹常开几个 agent 标签,`--continue` 会让它们都接到最新那一段。
- 不在启动时重跑自定义命令:它们可能有副作用(部署、写库),放进收纳盒让用户决定。

**未做**:恢复多个窗口的布局(只有一个窗口接上次显示的标签);"更新并重启"按钮(Ceteris 仍不下载、不运行安装包,见 ADR-018);输入框里没发出的字和等批准的那一步(agent 自己不保存)。

#### ADR-038:文件夹默认模型与 effort,标签里换模型并看用量(2026-11-10)

**背景**:开发者要两件事:点开文件夹时,在终端列表上方有一行能设这个文件夹里 agent 默认用的模型;每个终端标签的左下角能设这个终端的模型和 effort。Claude Code 和 Codex 都要。标签里的菜单照 OMC HUD 的样子:能选模型和 effort,一直显示 5h、wk、ctx,其余放进"详情"折起来。

**决策**:

1. **只管 Claude Code 和 Codex**(模板 id `claude-code`、`codex`)。其他 agent 没有统一的模型参数,不做。
2. **文件夹默认值存在设置里**:`agents.folderDefaults` 是 `{ pathId, agent, model, effort }` 的列表。用列表不用对象,因为设置的深合并删不掉对象的键;字段为空表示跟 agent 自己的设置走,什么参数都不加;两个字段都空就删掉这一项。界面上不写"默认":没选时方括号里用灰字显示 agent 自己设置里的值(Claude Code 的 settings.json、Codex 的 config.toml,只读),菜单里没有单独的"默认"项,选回和 agent 设置相同的值就等于清空这个字段。文件夹里有某个 agent 的终端时才有它那一行,每个 agent 一行,和终端行一样高、一样缩进,写成 `CC [Opus] [high]`,只有彩色文字,没有底色和边框;模型和 effort 各自点开一个选择。石子视图打开文件夹时显示;列表视图只在被点开的那个文件夹下显示,别的展开的文件夹保持紧凑。
3. **新开终端用启动参数**:Claude Code 加 `--model` 和 `--effort`,Codex 加 `-m` 和 `-c model_reasoning_effort=<级别>`。值只允许字母、数字和 `. _ - [ ]`,别的一律拒绝,不做转义。`-c` 的值不加引号:Codex 把不是合法 TOML 的值当普通字符串读,这样同一段文字在 pwsh、cmd、bash 里都不会被改。Codex 0.167 有 `-c` 时不连共享的后台服务,开机提示里会多一条警告,功能不受影响。
4. **Claude Code 新开时带 `--session-id <uuid>`**(本机、不是恢复对话时),Ceteris 因此确切知道每个标签的对话记录是哪个文件,不会把别的标签的数字算到这个标签头上。
5. **标签里换模型 = 在同一个标签里重启 agent**:先清掉输入框里打了一半的字(Ctrl-K、Ctrl-U 各按 30 次,每次单独发送:一次发出去会被当成粘贴;Claude Code 的 Ctrl-U 一次只删一行折行),敲 `/exit`,屏幕上的输入行正好是 `/exit` 才按回车,否则删掉 `/exit`、什么都不发送(2026-11-10 一条没清掉的长链接加上 `/exit` 被当成提问发给了 agent);然后等 Ceteris 的 shell 钩子报告提示符回来(OSC 1337,SessionManager 新增 `shellPrompt` 事件),再敲同一条命令,加上新的启动参数和恢复对话的 id(`claude --resume <id>`、`codex resume <id>`)。id 取 agent 退出时自己打印在屏幕上的那个(Claude Code 打 "claude ... --resume <id>",Codex 打 "codex resume <id>"),所以 `/clear` 之后也对;没打印时只用确定的 id(Claude Code 的启动 id),从不按"文件夹里最新的文件"猜,那可能是别的标签的对话。完全没有 id 时开始新对话,并告诉用户。标签还是原来那个 session:位置、名字、角色都不变。命令里的每个词只能是字母、数字和 `. _ = -`,不做任何引号转义(pwsh、cmd、bash、zsh、fish 的规则各不相同),做不到就不换。agent 正在干活、在等批准、SSH 标签、模板不在 agent 退出后保留 shell 时不换;20 秒内等不到提示符就不再输入任何东西。bash 标签原来 agent 退出后接手的是不带钩子的 `bash -i`,收不到提示符报告,现在改为 `bash --rcfile <钩子> -i`。
6. **用量从 agent 自己的文件读**,只读,不联网。Claude Code:对话记录 `~/.claude/projects/<文件夹>/<id>.jsonl` 给出提问数、工具 / 子 agent / skill 调用数、todo、上下文 token;装了 OMC 时,`<git 顶层>/.omc/state/sessions/<id>/hud-stdin-cache.json` 里有 Claude Code 交给状态栏的整份数据,补上 5h、周限额、上下文窗口大小和花费。限额按账号算,本标签没有时借同一位置别的会话的。Codex:`~/.codex/sessions/年/月/日/rollout-*.jsonl` 里有模型、effort、上下文和两档限额;按 cwd 和开始时间对应到标签,Codex 的模型列表读 `~/.codex/models_cache.json`。每次只读新增的字节。
7. **选中标签的模型和 effort 放在分屏按钮那一行**:两个按钮,和分屏按钮一样大(32px 高)、一样的块圆角(`--block-radius`,统一圆角),垂直居中对齐;不填充,悬停时也没有底色(边框加粗代替),边框就是整个按钮的外框,1px 线宽,颜色是渐变色(主题主色到主题第二强调色 `--color-accent-secondary`,主题没有第二色时只用主色),文字是彩色的(模型用主色,effort 按档位着色)。按钮的左边缘和终端里 OMC 状态栏(Codex 的底栏也一样)的文字对齐:两者都从终端左边第 3 格开始,按钮按选中标签所在分屏的终端实际测量;终端比按钮晚出现(新窗口、新标签、换布局)时会等它出现再量,字号、分屏布局、窗口大小变了会重新对齐。这里只管模型和 effort:5h、wk、ctx 等用量开发者放在 OMC 状态栏里看,不在这里重复。标签启动时没选模型或 effort 时,按钮显示 agent 报告的值(每 15 秒读一次选中标签的文件),再没有就显示 agent 自己设置里的值,不写"默认"。这一行本来就在,不占终端的空间。点模型或 effort 马上出菜单;agent 在忙时菜单照样出来,选项变灰并写明原因;切换期间显示"正在换成 …",结束后弹提示。先后试过浮在终端上的芯片(挡住 agent 最下面一行)、终端下方单独一条底栏、带用量百分比的一行字,开发者都改成了现在这样。

**为什么不是别的方案**:
- 不用 agent 自己的 `/model`、`/effort`:2026-11-10 实测 Claude Code 2.1.322 的 `/model sonnet` 回答"saved as your default for new sessions",会改掉用户在所有地方的默认模型。Codex 的 `/model` 很可能同样写进 config.toml,没有实测。启动参数只对这一次运行有效。
- 不靠屏幕判断 agent 已退出:Claude Code 退出后最后一帧还留在屏幕上;shell 钩子的提示符报告是确切的信号。
- 不在没有 OMC 时自己去调限额接口:那要读用户的登录凭据并联网。没有 OMC 时 Claude Code 的 5h / wk 显示"—",上下文只显示 token 数。

**未做**:其他 agent 的模型;SSH 标签的用量和换模型(文件在远端);输入框里打了一半的字在重启时会丢;OMC 的模式、后台任务、正在跑的子 agent 列表没有放进详情。

#### ADR-034:新建页只显示装了的 agent,常用的几个有小动画(2026-11-10)

**背景**:新建页的 Agents 区把七个内置 agent 全列出来,多数用户只装了一两个,其余按钮点下去只会得到一个“命令不存在”的终端。状态点(空心表示没装)已经知道答案,但只是标注,没有收起来。另一方面,用户每天点的往往就是同一两个按钮,页面对此没有任何表示。

**决策**:

1. **本机文件夹的新建页只显示 PATH 上找得到命令的内置 agent。** 新增 `cmd:agent:list-installed`,只扫 PATH,不跑 `--version` 也不联网,几毫秒内返回,所以 Agents 区等它回来再画,不会先画满再抽掉几个。没有检测规则的模板(用户自定义的)照常显示。SSH 和 WSL 文件夹里 agent 装在另一台机器或另一个发行版里,本机 PATH 说明不了什么,照旧全显示。一个都没装时 Agents 区留一行提示,告诉用户装好就会出现在这里;设置里的模板列表不受影响,仍然列出全部。Agents 标题右边有一个刷新按钮:刚装好一个 agent 不用重开页面,点一下就丢掉缓存重新扫 PATH、重新查版本。
2. **每个按钮的点击次数记在 `template-usage.json`。** 计数在 `cmd:session:create` 的处理里做,只有用户自己的点击走到那里(agent 经标签控制开的标签直接进 SessionManager),所以计数就是“用户常点哪个”。shell 按钮按 `shell:<shellId>` 分开计,PowerShell 和 Git Bash 是两个选择。不进 settings.json:设置每写一次都广播到所有窗口。
3. **常用的定义在 `src/shared/template-usage.ts`,渲染端自己算。** 30 天内点过 3 次以上的按钮才算,按次数排,最多三个:第一名是“最爱”(favorite),其余是“常用”(frequent)。只在当前页面上的按钮里排,隐藏或没装的模板不占名额。页面顺序不变:动画是标注,不是排序,免得肌肉记忆失效。
4. **动画只动图标,不动卡片。** 页面打开时常用按钮的图标按先后依次起跳一下,悬停时摇一摇,按下去整张卡片缩一点;最爱的图标角上多一颗小星,平时半透明,每隔几秒眨一下,悬停时转一圈。卡片不动所以网格不抖;系统开了“减少动效”时由 global.css 末尾的统一规则关掉。

**未做**:右键 + 号的快捷启动扇形仍显示设置里勾选的全部选项,不按是否安装过滤(那是用户手动勾的);常用按钮不自动排到前面;不提供关掉动画的开关(减少动效已经覆盖了需要它的用户)。

#### ADR-032:远程设置交给用户自己的 agent 带着做,Ceteris 只给指南和入口(2026-11-09)

**背景**:开发者要一份详细的 SSH 设置指南,按操作系统和角色(这台电脑做主机,还是去连别的电脑)分开,并且由用户自己的 AI agent 带着用户做完,包括装缺的依赖。入口在用户点标题栏的 Local 徽标或打开设置的远程分类时,先问一句,说"好"才开始。13.2 不做内置 AI 助手,所以指南必须交给用户已有的 agent。

**决策**:

1. 指南是两份 markdown 文件(`guides/remote-setup-host.md`、`guides/remote-setup-client.md`),英文写给 agent 读,每份按 Windows / macOS / Linux 分节:先问清对面是什么、怎么连通(推荐 Tailscale,不开公网端口),再查缺什么并装(OpenSSH 客户端和服务端、Tailscale、tmux、ssh-agent 服务、macOS / Linux 上保存密码要用的 sshpass),启动 sshd(Windows 还要防火墙规则和 DefaultShell),找出 `user@address`,生成和安放密钥(Windows 管理员用 `administrators_authorized_keys` 加 icacls),测试、排错表,最后填 Ceteris 的 SSH profile 或 `~/.ssh/config`,顺带说明 Ceteris Link。装好的 Ceteris 把 `guides/` 作为 extraResources 放在 asar 外,dev 用仓库里的那份;`cmd:guides:remote-setup-paths` 返回两份文件的绝对路径。
2. 粘给 agent 的是一行提示(`src/shared/remote-setup-guide.ts`,中英各一版,按界面语言选):说明这台电脑的角色和系统、指南路径、先查再改、缺的帮装、改动前征得同意。一行是为了 agent 不把它折成 "[Pasted text]",用户按 Enter 前能看到全文。和协调者引导一样只粘不发。
3. agent 标签用快捷启动列表里第一个 agent 模板(跳过 shell / admin-shell),没有则 Claude Code;在选中的本地文件夹里开,SSH 文件夹和 WSL 路径退回主目录。等 agent 启动画面安静下来再粘(`waitUntilSettled`,从协调者引导搬到 type-into-terminal.ts 共用),30 秒还没好就把提示放进剪贴板并提示。
4. 两个入口。标题栏徽标:还没有任何 Tailscale 主机和 SSH profile、也没回答过时,点一下先弹气泡问"连接另一台电脑?",选"好"再选角色;回答过之后照常弹菜单,菜单末尾多一项"让 AI 帮我配置…"(`view-menu.ts` 的 `setup-guide`)。设置 → 远程 顶部:没回答过时同一张问题卡,回答过后缩成一行加"开始"。远端视图里不问也不列(那里的设置属于 Host)。
5. "回答过"存 `behavior.remoteSetupGuideSeen`,默认 false,老设置文件补 false,所以升级后没配远端的用户也会被问一次;所有窗口同时停止再问。

**未做**:不自动按 Enter;不检测 agent 是否已安装(模板缺失时和平常一样报错);指南只有英文(agent 按提示用用户的语言交流);不做 Ceteris Link 的分步引导,Link 面板原有的三步提示保留。

#### ADR-037:agent 更新时关掉再开回来,接上对话(2026-11-10)

**背景**:Claude Code 这类 agent 更新时必须停掉正在跑的进程:Windows 上运行中的 exe 被锁,`npm install -g` 直接失败;其他平台能换文件,但开着的终端仍跑旧版。此前的做法是等用户自己把该 agent 的终端全关掉再升级(`waiting` 通知),用户关掉就丢了对话上下文,开回来还要重新说一遍做到哪了。开发者要的是:新建页的 agent 行提示有更新时,问一句要不要"整体重载",选了就全自动。

**决策**:

1. **先问再动**。新建页状态点被点、或通知里点按钮时,如果该 agent 有本机终端开着,弹一个三选对话框:关掉再开回来 / 只更新 / 取消。对话框写清会关几个、几个在跑、开回来后会发生什么、不碰什么。没有终端开着就照旧直接跑升级命令。通知上的"关掉再开回来"按钮只在本窗口看到该 agent 有终端开着时出现。
2. **只动这个 agent**。按 `templateId` 匹配,SSH 终端和退出的终端不算;其他 agent、纯 shell 的终端一律不碰,因为它们不占这个 agent 的可执行文件。纯 shell 里手动敲出来的同一个 agent(屏幕上有它的标记)只在对话框里提醒"可能让更新失败",不替用户关。
3. **顺序固定**:关掉 → 在可见终端里跑升级(复用 `startAgentUpgrade`,成功自动关闭)→ 强制重查版本 → 按原来的创建顺序开回来。升级失败或根本起不来,终端也照样开回来;通知里写明"没有更新成功,仍是 x 版"。这样用户的终端永远回来,而且通知里的版本号说明开回来的终端跑的是哪一版。
4. **接上对话**用各 agent 自己的命令行参数,追加在模板 args 后(`SessionManager.createSession` 新增 `extraArgs`,其余按模板):`claude --continue`、`codex resume --last`、`opencode --continue`、`gemini --resume latest`;copilot、cursor、aider 按文档填,本机没核对。开回来的终端在 8 秒内就退出,当作参数不被接受,不带参数再开一次。没有参数的 agent 直接重开,对话框会说"开回来的是新对话"。
5. **continue 只发给关闭时 `agentPhase` 为 working 的终端**,而且等它重新到提示符再敲:`agentPhase` 变 done 之后还要 1.5 秒没有任何输出,屏幕上有输入框标记(Claude Code / Codex)才算;刚 spawn 时 phase 就是 done 但横幅还在画,那时敲进去的字会丢(2026-11-10 实测)。90 秒没到就不发。结束通知指向第一个收到 continue 的终端,用户点一下就能确认它接着干了。在等用户批准(blocked)的不发,因为那本来就该由用户决定。名字(手动改过的)和角色(协调者等)原样恢复,显示在窗口里的那个终端仍显示在那个窗口。
6. **与后台自动升级的关系**:同一个 agent 的后台升级正在跑时拒绝重载(两边一起升级同一个全局包会撞车);等着的自动升级(`waiting` 倒计时)交给重载,不算跳过版本。同一个 agent 同时只允许一次重载。

**为什么不是别的方案**:
- 不在升级结束后让 agent 自己检测新版本并重启:agent 没有这种能力,Ceteris 也不该往终端里注入它看不见的指令。
- 不保留 PTY 只换进程:conversation 在 agent 自己的文件里,重开 `--continue` 就够了,保 PTY 没有收益。
- 不做成设置项"更新时自动重载":关终端是有感的事,每次问一句比默默关掉安全。

**未做**:不能恢复 agent 没有自己保存的状态(待批准的那一步、输入框里打了一半的话);不替用户关纯 shell 里手动跑的 agent;SSH 终端里的 agent 是远端的另一套安装,不在范围。

#### ADR-036:闲置标签收进收纳盒,带着 resume id 随时拿回(2026-11-10)

**背景**:开发者一天里开很多 agent 标签,做完的标签常常几小时、几天都不关。每个标签背后是一个 Claude Code 或 Codex 进程(几百 MB)加一份 headless 终端,放着不动也占内存。手动一个个关又怕丢掉对话:Claude Code 和 Codex 都能用 id 把对话续上,只是用户记不住 id。

**决策**:

1. **收纳 = 杀进程 + 记住怎么回来**。收起一个标签时,main 结束它的进程、释放 headless 终端(与关闭完全相同,`sessionDestroyed.reason = 'shelved'`),只在 `shelf.json` 里留一条:名字、文件夹、模板、cwd、时间,以及 agent 的会话 id。不保存屏幕内容:续上对话是 agent 自己的事,`claude --resume <id>` / `codex resume <id>` 从它们自己的记录文件重建。普通 shell 和其他 agent 也能收,拿回来只是在同一文件夹按同一模板重开。
2. **自动收纳的规则在一处**(`shared/shelf.ts` 的 `shelveBlocker`):设置 `behavior.shelveIdleAfterHours`(0 关,可选 1 / 3 / 5 小时、1 / 3 / 5 天)。"闲置"按最后一次输出、按键或退出算;`state === 'active'` 或 `agentPhase === 'working'` 不收;有角色(协调者 / Fintuner)的标签是用户特意摆的,不收;某个窗口正在显示的标签就在用户眼前,不收;停在批准提示的和已退出的照收。main 每分钟扫一遍,每次读设置,改了下一分钟生效。右键标签的"收进收纳盒"不看时间,但 agent 正在工作时拒绝。
3. **resume id 两条来路,先报后找**。ceteris-tabs 插件新增 SessionStart 钩子(`hooks/announce-session.mjs`),Claude Code 每次启动、`/clear`、resume 都把 `session_id` 经管道新操作 `agent-session` 报给 Ceteris,任何活着的标签都能调(同 ADR-033 的 open-file,不要求协调者和扩展)。没报过的(没装插件、Codex)在收纳时按文件夹和时间去找:Claude Code 看 `~/.claude/projects/<cwd 的 slug>/*.jsonl`,Codex 看 `~/.codex/sessions/年/月/日/rollout-*.jsonl` 首行 `session_meta` 的 cwd;候选文件的修改时间必须在标签创建之后、最后一次动静一分钟之内,取最新的。两个同文件夹的标签靠这个时间窗分开:闲置那个的文件早就不再变了。
4. **收纳盒在工作者标签行最左边**,只在盒里有东西时出现,灰色、圆形,和快捷启动图标同尺寸。点开是列表:模板图标、名字、文件夹、多久前、能否续聊;点一行恢复到本窗口并切到它的文件夹,行尾 × 移除一条,顶部"清空"。恢复先开新标签再删条目,启动失败的标签留在盒里。
5. **动画**:标签收起时在原位缩小、向左滑进盒子淡出,盒子接住后弹一下、盖子翻开又合上;盒子第一次出现放大弹入,最后一条拿走后缩小消失;列表从盒子的角长出,行依次淡入;移除的行向右滑出并收起高度,清空时逐行错开。系统减少动效时全部不播。为了让窗口在标签被销毁前拿到它的信息,`evt:shelf:changed` 先于 `evt:session:destroyed` 发出。
6. **持久化**:`shelf.json` 最多 100 条,重启后还在。这是 ADR-004"session 用完即弃"的一个有意的例外:盒子里存的不是 session,是"还能回来的入口"。

**未做**:SSH 标签恢复时重新登录(走和新建一样的 profile 流程,tmux 不自动 attach);其他 agent(Gemini、OpenCode 等)的续聊;Codex 的主动上报(它没有 hook,`notify` 要改用户的 config.toml);收纳盒里按文件夹分组。

#### ADR-035:agent 停下来等用户决定时,弹消息指到那个标签(2026-11-10)

**背景**:开发者同时开着好几个 Claude Code 标签。Claude Code 有时不是要批准,而是用 AskUserQuestion 摆出几个选项让用户选("Which colour do you prefer? 1. Red 2. Blue 3. Type something. 4. Chat about this"),然后一直等。ADR-021 只认批准提示("Do you want to proceed?" 加一行 Yes),这种选择提示被当成 done,标签不变色;而且就算变色,用户在别的标签或别的窗口里干活,也看不到。

**决策**:

1. `agent-phase.ts` 把选择提示也判成 `blocked`:屏幕末尾有 "Chat about this" 选项行,或者有 "Enter to select … Esc to cancel" 页脚且有一行带指针的编号选项。页脚措辞别的菜单也用,所以不单靠页脚。措辞按 Claude Code 2.1.319 在 2026-11-10 的录屏,Claude Code 改措辞时退回原来的 done,不会错判。
2. 不加第四种 phase:对用户来说批准和选择都是"agent 停下来等我",标签的呼吸警告色、ceteris-tabs 的 `wait_for_tab`、协调者的处理方式全都一样。标签提示文字从"等待你批准"改成"等你决定"。
3. 新增 `AgentChoiceNoticeBridge`:每个窗口看着 store 里各 session 的 agentPhase,某个 session **从别的状态变成 blocked**、而且它的终端不在本窗口屏幕上(没选中、也不在分屏里)时,弹一条警告色 toast"X 在等你决定",按钮"去看看"。跳转沿用侧栏点击的规则(8.4):本窗口持有或无主就在这里选中(无主先接管),别的窗口持有就聚焦那个窗口。agent 继续干活、用户看到了它、或标签关了,toast 自己消失;不然一直留着,直到用户关掉它。
4. 窗口打开时已经 blocked 的 session 不弹:那不是"刚发生"的事,标签上的警告色足够。
5. 不用系统通知,不加设置开关:开发者要的是"在 Ceteris 里指到那个标签"。toast 只在标签不在眼前时弹、一次提示一条,没有可调的东西。
6. toast 上的"选项"按钮把它展开成提示本身:main 从那个标签的屏幕读出问题和编号选项(`cmd:session:read-choice`,规则在 `agent-phase.ts` 的 `readChoicePrompt`:编号必须从 1 依次数上去,且有一行带指针,agent 回答里的编号列表就不会被当成提示),用户在 toast 里点一项,main 重读一次屏幕核对提示没变,再按指针位置发方向键和回车(`cmd:session:answer-choice`)。发方向键而不是数字键,因为 Claude Code 各种提示里数字键的作用不一样,方向键走哪个列表都一样。要打字的选项("Type something."、"Chat about this"、"No, and tell Claude what to do")不在 toast 里选,点了就跳到标签。批准提示同样能这么回答。Toast 组件为此多了可展开的 `detail`。
7. toast 不再画在 MD3 snackbar 的反色底上,改画在主题自己那一极的高层容器(`--md-surface-container-high` 加 outline 和投影)上:深色主题的通知是深的,浅色主题的是浅的。反色底在浅色主题上是一块深棕色,展开的选择面板和页面格格不入。2026-11-10 在 33 套主题(每个系列都有深浅各几套)上截图核对过。
8. 面板覆盖 Claude Code 的全部提示形态(2026-11-10 录屏核对,2.1.319 到 2.1.322):

   * **Type something**:指针一到这行它就变成输入框,打的字取代标签,回车提交。面板在这项下面展开一行输入框,发送时 main 依次发方向键、(退格清掉先前打的字)文字、回车,每段之后等屏幕显示到位才发下一段,否则文字会落在旧的那行上,数字还会被当成选项。多选列表里打字就已勾上,回车会取消,所以不按回车。
   * **Chat about this**,以及旧版批准框的"No, and tell Claude what to do":回车会拒答并回到 Claude 的普通输入框。面板的输入框可以留空(只拒答);有留言时 main 等提示离开屏幕再把留言打进输入框并回车,Claude 还在回应拒答时它会排队。新版批准框最后一项只是"No",按普通选项处理。
   * **多个问题**:顶上有页签"← ☐ Colour ☒ Size ✔ Submit →",回车作答并翻到下一题,最后是没有页脚的提交页("Review your answers … Ready to submit your answers? 1. Submit answers 2. Cancel")。提交页原来不算 blocked,现在按"Ready to submit your answers?"加带指针的选项判为 blocked。面板每次回答后重读屏幕,同一条 toast 里接着显示下一题和提交页,页签显示进度。
   * **多选**:选项带 [ ] / [✔],回车是勾选;列表里还有一行不带编号的 Submit,方向键也会停在它上面,所以读出的每个选项带"方向键停靠位"而不是用编号推算。面板勾完后点"选好了,下一步"发 Tab 翻页。
   * 读选项时以屏幕上最后一段从 1 数起的编号为准,agent 回答里的编号列表在提示上面也不会被当成选项;选项下面缩进的行(说明、折行的长选项)作为说明显示。

**未做**:系统通知(窗口最小化时看不到 toast);Codex 的同类提示(没有录屏,不猜措辞);在面板里退回上一页改答案(去标签里按 ←);批准框的"Tab to amend"附言。

#### ADR-033:任何标签里的 agent 都能把文件摆在标签旁边(2026-11-10)

**背景**:开发者问 agent 知不知道自己跑在 Ceteris 里,能不能"把回答写成 md,在 Ceteris 里开一个标签显示"。此前不能:agent 只拿到 `TERM_PROGRAM=Ceteris`,ceteris-tabs 的 `open_tab` 只会开终端,文件查看器只能从文件树点开。agent 写好文件后,用户还得自己去侧栏找。

**决策**:

1. ADR-024 的管道新增 `open-file` 操作,插件新增 `open_file` 工具。参数是文件路径(相对路径按目标标签的当前目录解析,因为文件通常是 agent 刚在那里写的)和可选的目标标签,默认是调用方自己。**任何活着的标签都能调**,不要求协调者,也不要求扩展打开:这是用户对自己那个 Claude Code 说的话(“把回答写成 md 在 Ceteris 里打开”),不该先去勾协调者。它展示的只是用户在文件树里也能点开的东西,而且只动调用方自己(或同文件夹里指名的)标签。其余工具仍按 ADR-024 只给协调者。
2. main 只做两件事:用 `fileViewKind` 确认是查看器认识的类型(md、txt、json、tex、代码和数据文件、pdf、图片),`stat` 一次确认文件存在;然后广播 `evt:file-view:open-requested`。不读内容。
3. 窗口收到事件后在 pdf-view-store 里以该标签为 key 调 `openPdf`,与文件树点击走同一条路。显示着那个标签的窗口立刻看到文件摆在终端旁边;多窗格放不下时沿用 MainPane 的现有规则。Markdown 仍先渲染,可切到编辑器(ADR-028)。
4. 插件的说明文字告诉 agent:要给用户看结果,就写成文件再 `open_file`。这就是 agent"知道自己在 Ceteris 里"的方式:不靠环境变量,靠工具描述。Claude Code 保存着自己那份插件副本,Ceteris 更新插件后要跑一次 `claude plugin update ceteris-tabs@ceteris`;设置 → 扩展 里插件的安装行不再只在协调者开关打开时出现,并多一行更新命令。
5. Codex 走同一个服务器:Codex 没有插件市场,MCP 服务器写在 `~/.codex/config.toml`。设置 → 扩展 的"Codex 也要用?"一键把 `[mcp_servers.ceteris-tabs]` 写进去(`src/shared/codex-mcp.ts`),命令是 Ceteris 自己的可执行文件加 `ELECTRON_RUN_AS_NODE=1`,`env_vars` 让 Codex 把标签的管道名和令牌转发给服务器。已有的项重写,其余内容不动。
6. 不开新终端标签,也不加"文件标签"这种新概念:文件查看器本来就是标签旁边的那块区域(14.6、ADR-016),再加一种标签会碰到 13.2 的通用编辑器红线。

**未做**:SSH 文件夹(文件在远端,main 无法 `stat`,查看器要走 SFTP 登录);让 agent 主动关掉或切换已显示的文件;真正的“文件标签页”(文件就在终端旁边显示,不另开标签,见第 5 点)。

#### ADR-031:Pili 主题系列照 PiliPlus 的种子色和默认算法生成(2026-11-09)

**背景**:开发者要一个像第三方 B 站客户端 PiliPlus(GPL-3.0)界面的主题系列。PiliPlus 没有手调的色板:它的整套界面是用一个主题色经 flex_seed_scheme 生成的 Material 3 配色,设置页列了 19 个主题色(默认绿 #5cb67b、B 站粉 #ff7299 和 17 个 Flutter Material 500 号色),默认算法是 material3Legacy(Flutter 3.19 之前的 `ColorScheme.fromSeed`)。

**决策**:

1. 新增 Pili 系列 38 款固定主题,id `pili-<颜色>` 和 `pili-<颜色>-dark`,顺序和名字同 PiliPlus 的 colorThemeTypes。菜单里英文名,附注中文标签。
2. 色板由 `src/shared/pili-scheme.ts` 按 material3Legacy 算:主色取种子色相、色度固定 48;secondary 色度 16;tertiary 色相 +60° 色度 24;neutral 色度 4,neutralVariant 色度 8;error 固定色相 25 色度 84。色调表用 flex_seed_scheme 的默认值,只有 surface 是 99 / 10。色阶用已有依赖 `@material/material-color-utilities` 的 TonalPalette,与 Flutter 同一套 HCT。灰色种子的色度也被抬到 48,主色带色相,与 PiliPlus 一致。
3. 深色的 surfaceContainerLow 存 PiliPlus 卡片实际画出的颜色:色调 10 叠 5% 的 onSurfaceVariant(它给深色 Card 设了 surfaceTintColor,elevation 1 的色调层)。Ceteris 用这个角色做标签页和终端底色,不这样做深色的页面和外框就同色。
4. 色板到界面 token 和终端配色的换算与 Legado MD3 系列共用 `legado-palette.ts`:外框 = surface,标签页 = surfaceContainerLow,菜单 = surfaceContainer,选中 = secondaryContainer。PiliPlus 给 AppBar、NavigationRail 和页面的也都是 surface,PopupMenu 和底部导航栏是 surfaceContainer,Card 是 surfaceContainerLow,所以不另写一套分工。
5. 固定文件由 `scripts/gen-pili-themes.mts` 生成(用 vite-node 运行,原因同 ADR-030 的 `server.deps.inline`);`pili-themes.test.ts` 核对 CSS、色板清单和现算结果三者一致,算法参数(主色色相和色调、页面色调、深色卡片色)符合上面的规则,并守 Legado 系列同样的对比度规则。

**未做**:PiliPlus 的其它 FlexSchemeVariant、自定义主题色和动态取色(Legado MD3 系列的 Custom / Windows Accent 已覆盖这类需求)、纯黑深色模式。

#### ADR-030:Legado MD3 主题可以用种子色和 Windows 强调色实时生成(2026-11-08)

**背景**:Legado MD3 系列最初只收了 legado-with-MD3 的 11 套固定配色。开发者要求再带上它的进阶配色功能:自定义种子色加调色风格、跟随系统颜色的动态取色、对比度档位。

**决策**:

1. Legado MD3 系列新增四个主题:`legado-md3-seed`、`legado-md3-seed-dark`(种子色来自设置)和 `legado-md3-accent`、`legado-md3-accent-dark`(种子色是本机强调色)。Legado 在 Android 上取壁纸色,桌面上对应的是 Windows 强调色。
2. 色板用 Google 的 `@material/material-color-utilities` 0.4.0 生成,与 Legado 用的 materialkolor 同一套算法。风格照 Legado 的 ThemeResolver 列九种(Tonal Spot、Neutral、Vibrant、Expressive、Rainbow、Fruit Salad、Monochrome、Fidelity、Content),对比度三档对应 contrastLevel 0 / 0.5 / 1,规范版本用 2021,与固定配色一致。开发者 2026-11-08 批准了这个依赖。
3. 色板到界面 token 和终端配色的换算从生成脚本移到 `src/shared/legado-palette.ts`,固定主题和实时主题共用;单测核对固定主题的 CSS 正是它算出的结果,并让 6 个种子色 × 9 种风格 × 3 档对比度 × 明暗共 324 套生成色板守同样的对比度规则。
4. renderer 的 `src/renderer/legado-dynamic.ts` 按设置和强调色生成四个主题,注入一个 `<style>`,结构同 ADR-026 的用户主题;终端配色从同一处取。拖颜色选择器时只预览本窗口,选择器关闭才写设置。
5. 强调色经 PlatformAdapter 的 `getAccentColor` / `onAccentColorChanged` 读取,Windows 用 Electron 的 `systemPreferences`;macOS 和 Linux 返回 null,主题回退到默认种子色。新增 `cmd:theme:accent-color`(Link 下本地执行)和 `evt:theme:accent-color-changed`。
6. 设置新增 `appearance.legadoSeedColor`(默认 #3b608f,晴空的主色)、`legadoPaletteStyle`(默认 tonalSpot)、`legadoContrast`(默认 standard),只在选了实时主题时用到。
7. 顺带修正终端色:红色从固定的 MD3 标准 error 色起步,不跟随色板的 error,否则高对比度下接近白色;深色主题的普通 ANSI 色从 tone 70 起步,bright 用 tone 80,原先 bright 在 tone 80 上再提亮,淡到认不出色相。

**未做**:从图片取种子色、背景图与透明主题、纯黑深色模式。0.4.0 的部分内部 import 缺 `.js` 扩展名,Vitest 用 `server.deps.inline` 让 Vite 转换它;应用构建本来由 Vite 打包,不受影响。

#### ADR-029:agent 标签的短标题,按用户的规则由模型写(2026-11-08)

**背景**:Claude Code 用 OSC 0 自己设终端标题(如 `✳ Refactor the session manager idle timer`),Ceteris 原样显示,标签太长。开发者要更短的标题,要能在设置里写一段规则,并且对所有 agent 生效。Claude Code 写标题用的模型不接受外部规则,所以规则只能由 Ceteris 自己写标题时使用。

**决策**:

1. 认作 agent 的标签:内置模板 claude-code / codex / opencode / gemini-cli / github-copilot / cursor / aider(`AGENT_TEMPLATE_IDS`),以及读屏认出 agent 阶段的标签(普通 shell 里手动启动的 Claude Code / Codex)。
2. 缩短总是生效,不需要 API:agent 的 OSC 标题去掉开头的转圈符号,超过 `ai.tabTitles.maxChars`(8 到 60,默认 24)时在词边界截断并加 …,没有空格的中文直接截。原标题存在 `agentOscTitle`,作为请求模型时的提示。
3. AI 标题 `ai.tabTitles.enabled` 默认关,因为屏幕末尾会发给 API。开启且 next prompt 的 API 可用(ADR-025 的 OpenRouter key,或本地地址)时,`AgentTitler` 在每轮结束后请求一次,模型、key、地址、花费统计都与 next prompt 共用。
4. 一轮结束的判断分两种。Claude Code / Codex 用 ADR-021 的 agentPhase:working 变 done,启动后第一次 done 不算(屏幕上只有欢迎页)。其他 agent 读不了屏,用"上次标题之后按过回车,输出随后停下"(active 变 idle);一轮中间停顿较久时可能提前起标题,同一次回车只起一次。
5. 请求带上当前标题,模型认为任务没变时回答 KEEP,标题不动。每个标签同时只有一个请求;请求期间又结束一轮,只在请求结束后补一次。
6. 优先级:手动改名最高,模型标题不覆盖它(`setAiTitle` 不置 `manuallyRenamed`,用户随时可以再改);AI 标题开着时,模型标题之后到来的 OSC 标题不再覆盖它;关掉后 OSC 标题照常接管。
7. 规则 `ai.tabTitles.guide` 最多 2000 字,留空用 `AGENT_TITLE_DEFAULT_GUIDE`(二到四个词,像简短的提交标题,用用户的语言,不带引号和结尾标点)。

**未做**:自定义模板不认作 agent(模板没有"这是 agent"的标记);只按模板认的 agent 在普通 shell 里手动启动时不认;"恢复自动标题"的右键菜单仍未接上(main 端 `clearManualRename` 已有)。

#### ADR-028:编辑 .md 和 .tex,扩展 ADR-016(2026-11-08)

**背景**:开发者要求在文件面板里也能改 Markdown 和 LaTeX 文件。ADR-016 只开放了 txt 和 json。

**决策**:

1. .tex 归入文本类型,与 txt、json 走同一个 TextFileView:2 MiB 以内可编辑,更大的分段只读。代码和数据文件后来按同样方式加入(ADR-040)。
2. Markdown 打开时仍显示渲染结果。标题栏有“预览 / 编辑”两个按钮,编辑时换成同一个 TextFileView,保存、冲突检查、未保存草稿和编码规则都与 ADR-016 相同。SSH 标签页里第二个按钮叫“源文本”,因为那里只读。
3. 从编辑切回预览时,有未保存修改就渲染草稿,并在上方提示“预览的是未保存的修改”,不必先保存才能看效果。没有草稿时立即刷新一次,保存的结果马上出现,不等轮询。
4. 有未保存草稿的 Markdown 文件重新打开时直接进入编辑,草稿不会藏在预览后面。
5. 允许保存的类型由 `isEditableTextFile`(src/shared/file-tree.ts)统一判断,main 的 text-writer 和 renderer 用同一条规则。

**不变**:没有保存快捷键,切换编辑和预览只有按钮(13.2 鼠标优先);不做语法高亮、格式化或分屏实时预览,这里只为顺手改一下文本,不是 IDE。

#### ADR-027:agent 跑完时的小庆祝,不打扰(2026-11-08)

**背景**:开发者想在用 Ceteris 干活时有一点可爱的鼓励,但不能打扰工作。2026-11-08 从七个方案的动画样稿里选了三个:圆点上的小星星(1)、样式随主题(4)、标题栏小石子(5)。

**决策**:

1. 规则:不抢焦点,不盖住终端文字,不出声,每次只播一次且不到一秒,播完留下的是已有的静止标记;系统开启减少动态效果时只留静止标记。
2. 触发沿用 ADR-021 的 `unseenDoneSessionIds`:圆点从无到有的那一刻播一次。`CelebrationBurst` 用当前值初始化"上一次",所以标签栏重挂、窗口刚打开时已经亮着的圆点不会重播。粒子 portal 到 body、`position: fixed`,标签栏和侧栏的 overflow 不会裁掉它。
3. 只在标签上播;顶部标签栏隐藏时改在侧栏圆点上播,两处同时播太吵。`CelebrationBurst` 不订阅 store,开关和主题由父级传入,侧栏 `SessionItem` 保持不调 `useAppState`。
4. 样式表在 `src/renderer/celebration-style.ts`:cutie / light-pink / fairyfloss 爱心,rose-pine 三套和 meizi 花瓣,`pearl-` 前缀一圈虹彩光环,business / windows-terminal 一个对勾,其余(含用户自定义主题)星星。颜色取主题的 `--md-primary`、`--color-accent-secondary`、`--color-success`。
5. 小石子 `TitlebarPebble` 放在窗口按钮旁,16px,`pointer-events: none`。看所有 session:有 `agentPhase=working` 时睁眼,任一 session working → done 时笑两秒(正在看的那个跑完也笑),否则打盹。前后比较用 `useLayoutEffect`,否则 done 那一帧会先画出打盹。
6. 设置:`appearance.celebrations` 默认 true,关掉后小庆祝和小石子都不显示;`appearance.pebble` 默认 false,因为它一直可见。

**未做**:命令跑完的鼓励(方案 2、7,后者要改 shell hook 上报退出码)、悬停时的鼓励话(方案 3)、当天的小芽(方案 6)。托盘和任务栏仍不动,与 ADR-021 一致。

#### ADR-026:用户主题是数据目录里的 CSS 文件(2026-11-08)

**背景**:开发者要求用户能自己定义主题,并有一份像 CSS 一样的标准模板可改。

**决定**:
1. 主题文件夹是 `<数据目录>/themes`,每个 `.css` 文件是一个主题,文件名生成 id `custom:<slug>`,`@name` 注释行是菜单里的名字。以下划线开头的文件不加载;首次使用时写入 `_template.css`,即带注释的标准模板。
2. 文件格式就是 CSS,变量名与内置主题相同(global.css 的 15 个 Layer 2 token),再加 `color-scheme` 和 `--terminal-*`。Material 外观层的颜色角色从这些 token 推导,所以用户主题自动得到完整外观。
3. renderer 把所有用户主题一起注入一个 `<style>`,每个文件包进 `html[data-theme='custom:x'], [data-theme='custom:x'] { ... }` 嵌套规则,`:root` 改写成 `&`。只有选中的主题作用于页面,菜单色块仍能显示每个主题的颜色;额外的规则也被限定在该主题内。`html` 让特异性略高于内置的 `:root` 块,注入顺序不影响结果。
4. 终端颜色由 shared 的解析器从文件里读出(xterm 不读 CSS)。缺的终端颜色退到界面颜色和一套标准 ANSI 色,只写界面颜色的主题也有可用的终端。
5. main 用 fs.watch 监视文件夹(150ms 防抖),保存后把新列表推给本机所有窗口。命令都在 LINK_LOCAL_ONLY_CHANNELS 里:主题文件在本机,远程窗口的主题本来就跟随本机。
6. 设置只校验 id 格式。选中的主题文件被删或改名时,renderer 显示默认主题并在菜单下提示,不改写设置。

**为什么不是别的方案**:
- 不做应用内取色编辑器:CSS 文件可以用任何编辑器改、复制、分享,保存即见效;编辑器是一大块 UI,而用户要的是模板。
- 不用 JSON:CSS 能顺带写其它规则(圆角、字体),变量名与内置主题一致,写主题的人改的就是应用实际读的东西。

#### ADR-025:下一步提示建议的 OpenRouter key 改为浏览器授权,加密保存(2026-11-08)

**背景**:下一步提示建议原来让用户在设置里粘贴 OpenRouter key。key 以明文写在 settings.json 里,有三个问题。第一,settings 会广播给每个窗口,并经 Ceteris Link 发给远程视图。第二,每次写盘都会复制一份到 settings.json.bak。第三,用户要去 OpenRouter 网站找 key、复制、粘贴,步骤多也容易贴错。开发者要求换一种更安全、更好用的方式,并且不要让用户粘贴。

**决定**:
1. 设置里只有一个"连接 OpenRouter"按钮。点击后 main 在 127.0.0.1 和 ::1 上开一个随机端口,用浏览器打开 OpenRouter 的 OAuth PKCE 授权页(`callback_url=http://localhost:<端口>/callback`,S256 challenge,随机 state)。用户登录并同意后,OpenRouter 回调本机端口,main 用 code 加 verifier 换到一个专用 key(标签 "Ceteris next prompt")。端口在回调、取消或 5 分钟后关闭。
2. key 用 Electron safeStorage 加密(Windows 上是 DPAPI,绑定当前用户和这台电脑)后写入 secrets.json,只有 main 读。settings 只保留 `ai.nextPrompt.keySaved` 标志,而且只有 main 能改它。
3. key 只发给 OpenRouter。API 地址改成别的(如本地 Ollama)时请求不带任何 key,自定义地址视为不需要 key。
4. 旧版本粘贴的 key 在启动时自动移进 secrets.json,然后把 settings.json 连写两次,让 .bak 里也不留明文。
5. 远程视图里不能连接或断开:浏览器会开在 Host 上。key 只存在 Host,远程视图照常经 Host 使用。
6. 导出包不含 secrets.json;导入时保留本机的连接状态。
7. 设置 → AI 助手只保留下一步提示建议。状态复核(BETA-006)几乎没人用,界面上隐藏,后端代码不动,默认关闭;已开启的用户不受影响。
8. 累计花费下方加一张近 14 天每日花费柱状图(next-prompt-usage.json 按本地日期记录,只留最近 30 天);常用消息按次数从多到少排列,次数在前。同一天用过几个模型时,柱子按模型分段堆叠:每天另记各模型的次数和花费,颜色按模型首次出现的顺序固定,最多 4 种颜色,其余并入灰色的"其他模型";图下有图例,悬停某天列出各模型的金额和次数。

**为什么不是别的方案**:
- 不只是把粘贴框改成加密存储:仍然要用户找 key、粘贴,开发者明确不要。
- 不用 OpenRouter 的"无回调"模式(页面显示 code 让用户抄回来):又变成了粘贴。
- 不把 key 放 Windows 凭据管理器(keytar 之类):需要新的原生依赖;safeStorage 已在用于 SSH 密码,效果相同。

**放弃的**:断开只删除本机这份 key,无法替用户在 OpenRouter 上作废它(作废 key 需要管理权限的 key);设置页提示用户到 openrouter.ai 的 Keys 页删除。自定义地址如果是需要 key 的云服务,目前不支持;等有人需要再加。Linux 上没有密钥环时 key 只保存在内存里,退出后要重新连接。状态复核用的 `ai.apiKey` 仍是明文,本次没有改。

#### ADR-024:协调者标签可以控制同文件夹的其他标签(2026-11-08)

**背景**:ADR-023 让用户把一个 agent 标成协调者。用户希望协调者里的 Claude Code 真能统筹:自己开新标签、给它们派活、读结果、关掉,而不是让用户在标签之间来回复制。这种能力很大,所以只给协调者。

**决策**:

1. 设置 → 扩展 新增“协调者控制标签页”(`settings.extensions.tabControl`),默认关。每次请求都现查,开关立即生效。
2. main 开一条命名管道(`tab-control-server.ts`,非 Windows 用 unix socket),管道名含 pid 和随机数,稳定版和测试版互不相通。每个新标签 spawn 时拿到 `CETERIS_CONTROL_PIPE`、自己的随机令牌 `CETERIS_CONTROL_TOKEN` 和 `CETERIS_CONTROL_NODE`(Ceteris 自己的可执行文件)。令牌只说明“我是哪个标签”,本身不授权;这三个变量也加进 spawn 的跳过列表,子标签不会继承父标签的令牌。
3. 授权在每次请求时按标签当前状态判断:标签存在、没有退出、`coordinator === true`、扩展已打开。取消协调者或关掉扩展,下一次请求就被拒。
4. 范围是协调者所在的文件夹(`pathId`):只列出、只能指名这个文件夹的标签。协调者不能关闭或输入自己的标签,避免自我循环;可以读和改名自己。
5. 新开的标签没有 owner 窗口,所以正在看协调者的窗口不会被切走,用户点那个标签才去看;尺寸先跟协调者一样。SSH 文件夹里不能新开,因为登录要走 ipc.ts 的 profile 处理。
6. 输入顺序是文本、命名按键、停 150 ms 后回车。Claude Code 把同一块里的文本和回车当成粘贴,只会换行不会发送。多行文本在程序打开了 bracketed paste 时包成粘贴。
7. Claude Code 这一侧是随 Ceteris 安装的插件 `extensions/ceteris-tabs`,与 ADR-019 共用本地 marketplace。插件只有一个无依赖的 MCP 服务器,用 `${CETERIS_CONTROL_NODE:-node}` 加 `ELECTRON_RUN_AS_NODE=1` 运行,用户不必另装 Node.js。不在 Ceteris 里时它不提供任何工具,别的终端不为它多花上下文。等待(`wait_for_tab`)由插件每秒轮询一次,管道始终一问一答。

8. 引导是叠在真界面上的动画导览(`CoordinatorTour.tsx`,步骤逻辑在 `@shared/coordinator-tour`),不挡点击。`settings.extensions.tabControlGuideSeen` 为 false 时启动就出现(新安装,或升级后第一次启动;老设置文件合并默认值后是 false),勾选协调者时也会出现。先介绍三个角色:Coordinator 盯着并指挥其他 Claude Code,Worker 是同一文件夹里接活的普通标签,Fintuner 读对话历史找省时间、提效率的办法;并说明这是推荐用法,不是内置功能,都是普通的 agent 标签。导览不假定用户用 Claude Code:指着标签栏末尾第一个 agent 图标,Fintuner 用和协调者同一个 agent;设置和插件两步只对 Claude Code 有用,协调者跑的是 Codex、OpenCode 等内置的其他 agent 模板,或用户点“不用 Claude Code”时跳过,并改为说明怎么用上方一行和“运行中 / 等你处理”筛选盯住 Worker。然后聚光灯加光标动画演示:点标签栏末尾的 agent 图标、右键标签、点菜单里的“协调者”;用户真的做了才进入下一步(每帧按状态判断)。之后指出上方一行,再教用户加 Worker(没有普通标签时指着标签栏末尾的 agent 图标,有了就圈出它们;Worker 不改名),然后打开设置、装插件(main 读 `~/.claude/plugins/installed_plugins.json` 判断装没装)、交代任务,Fintuner 也是一个 agent 标签,所以最后用同样的动画做一个:点 agent 图标、右键新标签、角色 → Fintuner;那一段里新出现的 Fintuner 都会粘贴一次提示,也留了“直接帮我开好”的快捷链接。最后一步指着 Fintuner 标签。标签右键菜单的“协调者”勾选改为 角色 子菜单:Worker(普通标签)、Coordinator、Fintuner。`SessionInfo.role` 记录角色,由 main 的 `SessionManager.setRole` 设置(`cmd:session:set-role`):有角色就同时设 `coordinator = true`(两种角色同级,都在上方一行,都能用标签控制管道),并把标签改名为角色名(按手动改名处理,agent 标题不会盖掉);清除角色时名字没被用户再改过就恢复原名。之前改名放在导览里,导览关掉后再勾就不改名,这次一并修掉。快捷链接也走 setRole,等 agent 启动安静下来后自动粘贴提示;“交代任务”一步也能把一个示例任务粘贴进 Coordinator。两处都只粘贴不发送,由用户按 Enter。提示有中文和英文两版(`@shared/coordinator-prompts`),各自按读者写,跟随界面语言;agent 30 秒内没起来就改为复制到剪贴板。“完成”或“不再提示”写 true;“稍后”只关本窗口。首次使用的快捷启动气泡还在时,导览先等它关掉。

**未做**:跨文件夹控制、协调者之间的分工、把子标签的输出主动推给协调者。

#### ADR-023:侧栏的“运行中 / 等你处理”筛选,以及协调者标签行(2026-11-08)

**背景**:同时开很多 agent 时,用户要逐个文件夹展开才知道哪些在跑、哪些在等自己。另一方面,用户常让一个 agent 统筹其他 agent;这个协调者所在的文件夹一关,它的标签就看不到了。

**决策**:

1. 侧栏标签栏最前面固定两个筛选“运行中”和“等你处理”,不是文件夹标签,不能改名、改色或删除。归类沿用 ADR-021 的规则(`src/shared/session-status.ts`):标签在波浪 = 运行中;`agentPhase` 为 blocked 或 done = 等你处理。普通 shell 安静下来不算等你处理,因为没有 agent 就分不清命令跑完了还是在等输入。
2. 两者一次只能选一个(两类互不相交,同时选只会得到空列表)。与文件夹标签是“且”:先按标签筛文件夹,再留下有匹配终端的文件夹,强制展开,只列匹配的终端。计数只数标签筛选后的文件夹,点下去看到的和数字一致。筛选状态属于本窗口,不保存。
3. `SessionInfo` 新增可选字段 `coordinator`,经 `cmd:session:set-coordinator` 由 main 广播,所有窗口一致。协调者标签按创建时间排在标签栏上方单独一行,不论打开的是哪个文件夹;下面一行不再重复它。行里的标签前写所属文件夹名,因为多个 agent 常常同名。点它先切到它的文件夹,再走原来的选中 / 接管 / 聚焦逻辑,所有权规则不变。
4. 标记随 session 存在,不持久化,与 session 不持久化的设计一致。
5. **修订(2026-11-10)**:用户反馈运行中漏掉了在跑命令的 pwsh 等 shell,等你处理应当只列刚跑完一轮的标签。改为:
   * 运行中 = agent 在 working,或 shell 的命令在跑。`SessionInfo` 新增可选字段 `shellBusy`:shell hook 每次画提示符都发 OSC 1337 CurrentDir,main 收到就置 false;此后用户按 Enter 置 true,直到下一个提示符。所以 `npm run dev`、ssh、长时间编译这类不出字的命令也算运行中,在提示符上打字不算。没收到过提示符的 shell(没装 hook,如部分远程)`shellBusy` 保持空,退回原规则:出字才算运行中。
   * 等你处理 = agent 停在批准提示 (blocked),或者跑完一轮而用户还没看过(renderer store 的 `unseenDoneSessionIds`)。shell 的一轮是一条命令,`shellBusy` true → false 时不在屏幕上就记为没看过。选中这个标签后它离开等你处理。看过的 done agent 不再算。

**未做**:协调者在窗口失焦时的提醒、协调者行的拖动排序。

#### ADR-022:Codex 公式渲染做成可选扩展,Ceteris 在显示层用 KaTeX 画(2026-11-08)

**背景**:开发者要 Codex 的回复也能显示排好版的公式。Codex CLI 没有插件或渲染钩子,终端里也不画图;它在 TUI 里把能认的 TeX 子集转成多行 Unicode 文字,Ceteris 根本看不到原来的 LaTeX。只有行内代码和它认不出的公式会原样到达终端。

**决定**:设置 → 扩展 新增第二项"Codex 公式渲染"(`settings.extensions.terminalMath`),默认关,打开后对已打开的终端立即生效。
1. `@shared/terminal-math` 在一行终端文字里找 `$$...$$`、`\(...\)`、`\[...\]`。`$$` 也是 PowerShell 的变量和 bash 的 PID,所以 `$$` 里必须有反斜杠、^、_ 或 {;`\(` 和 `\[` 本身就够。整行只有一个 `$$` 或 `\[` 公式时按 display 画,可以向下占最多两个空行。
2. `renderer/terminal-math-overlay.ts` 用 xterm decoration 在原文的格子上盖一层 KaTeX(新依赖 `katex`,MIT),背景用终端背景色挡住原文,pointer-events 关掉以免挡住选择。每次输出、滚动、缩放后重新扫可见行,原文变了的覆盖层就移除,Codex 重画活动区时不会盖住新文字。
3. 设置页按钮开一个新终端,敲入把一条指示加进 `~/.codex/AGENTS.md` 的命令(已有就跳过),不按 Enter。指示让 Codex 把公式写成行内代码 `$$...$$`(display,前后空一行)和 `\(...\)`(行内)。

**为什么不是别的方案**:
- 不用 math 代码块:Codex 渲染代码块时不显示围栏,终端里分不出哪段是公式。
- 不复用 TeX Live 渲染器:要装 TeX Live、ImageMagick、Git Bash,Windows 上一个公式几秒;KaTeX 在窗口里即时排版,颜色跟主题。
- 不改 Codex 本身:不是 Ceteris 能控制的程序。

**风险**:KaTeX 只支持 LaTeX 数学的一个子集,不支持的部分显示红色错误文字;行内公式压到一行高,复杂的分式会很小;覆盖层只认可见行里的文字,任何程序打印出符合规则的文字都会被画成公式。

#### ADR-021:标签页按 agent 的状态动画,不只按有没有输出(2026-11-07)

**背景**:波浪线表示"agent 在跑",但它只看最近有没有 PTY 输出。停在批准提示的 agent 和跑完的 agent 都没有输出,波浪线同样消失,用户看不出哪个 agent 在等自己。波浪线本身也太细太淡(4px 高,文字色),几乎看不出在动。

**决策**:

1. 一条规则:**动 = agent 不需要你;静止或呼吸 = 它在等你**。波浪线 = working;警示色呼吸的条和圆点 = blocked(等批准);主色圆点、闪两下后静止 = done 且用户没在看。
2. 状态从屏幕读,不从字节速率读。`SessionInfo` 新增可选字段 `agentPhase`,main 在每段输出后最多 300ms 内、以及进入 idle 时,用 `detectAgentPhase`(`src/shared/agent-phase.ts`)读 headless 镜像最后 60 行里的最后 20 个非空行(Claude Code 在工具输出和 spinner 之间留约十行空白,状态栏又占几行,按非空行数才不会把标志挤出窗口)。批准提示和 "esc to interrupt" 对任何 session 生效(在普通 shell 里敲 `claude` 打开批准框时,`detectAgent` 依赖的标志会被盖住);done 需要识别出 agent,普通 shell 安静下来仍是 null,沿用原来的输出驱动波浪线。
3. 提示文字以 2026-11-07 安装的二进制为准:Claude Code "Do you want to proceed?" / "Do you want to make this edit to …?",Codex "Would you like to run the following command?" / "… make the following edits?",两者工作中都显示 "esc to interrupt",选项行以 "Yes" 开头。agent 改了措辞时匹配不上,结果是退回输出驱动的波浪线,不会显示错的状态。
4. "没看到"记在 renderer store(`unseenDoneSessionIds`),不在 Tab 组件里:Tab 只为当前 path 挂载,其他文件夹里跑完的 agent 也要记住,侧栏圆点据此显示。只有 working → done 才记;选中该 session 即清除。
5. blocked 用 `--color-warning`:各主题都为它调过对比度。侧栏 idle 圆点本来就是这个颜色,blocked 时同色加呼吸;标签上 orphan 也用它,但 orphan 是文字颜色,blocked 是底部条和圆点。

6. 波浪线的形状跟着工作类型,速度跟着 token 速率(v1.14 起,2026-11-08 录屏后定)。`agentWork`:generating = 快而密的波纹,waiting = 慢而长、带呼吸的起伏(hooks、API 刚开始),tool = 近乎平的线上有一个脉冲走过;`agentPace` 0.25 到 1(按四分之一取整,一轮只发几次事件)让 generating 的波纹变快。renderer 用 `AgentWave.tsx` 以 SVG + requestAnimationFrame 画,形状参数每帧向目标缓动,切换时是变形而不是跳变;只在 running 或收尾时跑循环。普通 shell 和 Codex 没有工作类型,保持原来匀速的波浪。
7. 录屏(2026-11-08,Claude Code + Haiku,ping 一次再写一段话)推翻了两个假设。一是**字节速率分不出思考、写字和工具**:spinner 和计时器一直重绘,三段分别约 650、730、760 B/s,所以速度改用 spinner 行上的 token 计数("↓ 94 tokens"),它在生成时上涨、工具运行时不动。二是这一版的 spinner 行**没有** "esc to interrupt",working 的标志是 spinner 行本身(星形字符 + 随机动词 + 省略号)。工具运行的标志:描述行末尾带实时计时("● Running the ping command · 14s",括号外),下面一行 "⎿";工具结束后计时消失。Codex 没有录屏,只用 "esc to interrupt" 和批准提示。

**未做**:窗口失焦时闪任务栏、托盘光点按最紧急的 session 变色。等实际用一阵再决定是否需要。

#### ADR-020:`名称:` 在 Claude Code 和 Codex 里换成斜杠命令(2026-11-08)

**背景**:开发者想用同一套短名字在 Claude Code 和 Codex 里调命令。两个 CLI 都用 `/` 开头的命令,开发者希望把触发符放到名字后面:敲 `compact:` 就得到 `/compact`。

**决定**:设置 → 扩展 新增第二项"名称: 命令"(`settings.extensions.colonCommands`),默认关。
1. 列表存在 Ceteris 设置里,每项是名称和命令,命令留空即 `/名称`,也可以指向别的命令,例如 `plan` → `/oh-my-claudecode:plan`。默认放四个两边都有的命令:compact、model、init、status。名称不分大小写,最多 50 项。
2. 只在单词开头触发:名称在输入开头,或前面是空格。冒号被吞掉,Ceteris 按名称长度发 DEL 删掉名称,再敲命令,同一次写入。中文输入法的全角冒号同样触发。不按 Enter,CLI 自己的 `/` 菜单停在这条命令上,由用户确认。
3. renderer 的 `ColonTracker`(`shared/colon-commands.ts`)根据发出的按键重建当前输入行。Enter、Ctrl+C、Ctrl+U 之后回到输入开头;方向键、Tab、Alt 组合等跟不上的按键让行首变成未知,这时只有空格之后的名称才触发;单独的 Esc 不动输入,保持原状;终端替程序发的回复(DA、XTVERSION、颜色查询、焦点报告)不算按键。
4. 是不是 agent 用 `detectAgent`(与下一步提示建议同一规则):模板是 Claude Code / Codex,或屏幕上有它们的底栏。只在冒号刚敲在已知名称后面时读屏幕。

**为什么不是别的方案**:
- 不读 `~/.claude/commands` 或 `~/.codex/prompts`:开发者选择在 Ceteris 里列出名称;两个 CLI 的命令目录格式不同,也不覆盖内置命令。
- 不替用户按 Enter:有些命令要参数,而且误触发时用户还能退格改回来。
- 不在任意位置触发:`note: ...` 这类普通文字很常见,只认已保存的名称且在单词开头。
- 不违反 13.2:这是在终端里敲字,不是应用内快捷键。

**风险**:Ceteris 看不到 CLI 的输入框,光标被鼠标或历史记录移动后,跟踪可能与实际不符;最坏情况是名称被换成命令,退格即可。模板是 Claude Code 的标签在 agent 退出回到 shell 后仍算 agent。2026-11-08 在 Claude Code 2.1 和 Codex 0.166 上验证过 DEL 加命令的一次写入。

#### ADR-019:Claude Code 公式图片做成可选扩展(2026-11-08)

**背景**:开发者想在 Ceteris 里看 Claude Code 回复中排好版的 LaTeX 公式。社区插件 latex-math(atomashevic/claude-latex-math,MIT)只支持 kitty 和 Ghostty,而且不能在 Windows 上跑。Claude Code 只在两种情况下画图:终端支持 kitty 的 Unicode 占位符(xterm.js 没有),或者 XTVERSION 回复写着 iTerm2 3.5 以上。

**决定**:新增 设置 → 扩展 分类,第一项是"Claude Code 公式图片"(`settings.extensions.claudeMathImages`),默认关。打开后只影响之后新建的终端:
1. renderer 给终端装 `@xterm/addon-image`,只开 iTerm2 内联图片解码,并把 XTVERSION 回复成 `iTerm2 3.5.0`(`renderer/inline-images.ts`)。
2. main 的 OSC 1337 解析器把 `File=` / `MultipartFile=` / `FilePart=` / `FileEnd` 原样交给 xterm,只吃 `CurrentDir`。
3. Windows 上新 session 改用 node-pty 自带的 ConPTY 1.23(`useConptyDll`)。系统 conhost 自己抢答 DA1,比终端的 XTVERSION 回复先到;Claude Code 把 DA1 当作"回复到齐",于是认定终端不画图。
4. Claude Code 在图片格子里写 U+2800 加组合符作占位,字体没有盲文字形时会显示成方框。`placeholder-filter.ts` 把 U+2800 换成空格,丢掉紧跟的组合符;插件画不透明图片盖住它们。
5. renderer 把终端前景、背景色和格子宽高比报给 main,main 写到数据目录 `extensions/terminal-look.json`;新 session 拿到 `LATEX_MATH_LOOK_FILE` 和 `LATEX_MATH_BASH`(探测到的 Git Bash),插件每次画图现读这个文件,所以主题改了也跟着变。
6. 插件的 Ceteris 分支放在仓库 `extensions/claude-latex-math`,`extensions/` 本身是一个本地 marketplace(`extensions/.claude-plugin/marketplace.json`,名字 ceteris),随应用装进 `resources/extensions`(electron-builder extraResources,放在 asar 外)。设置页向 main 要这个目录(`cmd:extensions:get-marketplace-dir`,dev 用仓库目录),"在新终端里输入命令"按钮开一个新终端敲入 `claude plugin marketplace add <目录>` 和 `claude plugin install latex-math@ceteris`,不按 Enter,用户按 Enter 就是同意。不依赖网络或 GitHub 分支,插件版本总与应用一致。
7. 生产 CSP 的 `script-src` 加 `'wasm-unsafe-eval'`:addon 用 WebAssembly 解 base64。缺它时 handler 抛错,整个终端的输出就停了。这一项不随开关变化,因为 CSP 在窗口加载时就定了。

**为什么不是别的方案**:
- 不默认打开:自报 iTerm2 会让其它程序以为在 iTerm2 里;换 ConPTY 影响所有 Windows 终端。只给主动要的人。
- 不走 kitty 协议:xterm.js 的 Unicode 占位符还没做(xtermjs/xterm.js#5711),Claude Code 的 kitty 路线只用占位符。
- 不用环境变量传颜色:第一个 session 往往在终端界面挂载之前就启动了,那时还没有颜色;环境变量也跟不上主题切换。
- 不只依赖上游插件:上游把 Windows 列为不支持,在 Ceteris 里也不会画图。

**风险**:打开后,Windows 新终端换了 ConPTY 实现,行为细节可能与系统 conhost 不同;Windows 上一个公式要几秒才排好,排好之前 Claude Code 显示 LaTeX 源码;自带的插件分支要跟上游同步。

#### ADR-018:检查 GitHub Releases 的新版本,只给下载直链(2026-11-08)

**背景**:开发者要求应用自己发现 GitHub 上的新版本,并直接给出适合用户系统的安装包下载链接。13.1 原先把“自动更新”整个列为 V1 不做。

**决定**:
1. main 进程的 `UpdateChecker` 用 `net.fetch` 读 `https://api.github.com/repos/Fanisting/ceteris/releases/latest`(匿名,User-Agent `Ceteris-Updater`,不带任何用户信息),跳过 draft 和 prerelease,按数字比较 tag 与 `app.getVersion()`。
2. 选文件的规则在 `src/shared/update-check.ts`,纯函数、有单测:Windows 给 Setup exe,portable 运行时给 Portable exe;macOS 按 CPU 给 arm64 或 x64 的 dmg;Linux 以 AppImage 启动给 AppImage,否则 Debian 系(`/etc/debian_version`)给 deb、Red Hat 系给 rpm,都没有再退到 AppImage。没有匹配的文件时链接发布页。
3. 定时检查:启动 15 秒后一次,之后每 6 小时。只在 **stable** 且 `settings.behavior.autoCheckUpdates` 为 true(默认)时跑。beta 和 dev 是本地测试构建,版本号跟着 stable,让它们去下 stable 安装包只是噪音;它们仍可在关于页手动“立即检查”。
4. 提示是安静的:侧栏设置按钮上一个小圆点(点进去直接到关于页),关于页有“下载 vX.Y.Z”和“更新说明”两个按钮,Windows 托盘菜单顶部一项“有新版本 vX.Y.Z,点击下载”。没有弹窗,没有系统通知(13.1)。
5. 失败(离线、代理、GitHub 匿名限流每 IP 每小时 60 次、返回内容不对)只记 warn 日志并在关于页说明原因,不弹窗;之前查到的新版本继续显示。

**为什么不是别的方案**:
- 不用 electron-updater:要新增依赖(AGENTS.md 边界 2),还需要发布时生成 latest.yml 和签名;更重要的是自动安装会替换正在运行的程序,关掉用户所有终端会话,这必须由用户自己决定时机。
- 不检查 beta 通道的 prerelease:目前发布流程只发正式版,beta 只在本地构建。

**放弃的**:应用内下载进度和校验;安装仍是用户双击下载好的文件。

#### ADR-017:PDF 实时预览改用 pdf.js,SFTP 登录提示走 askpass 中继(2026-11-07)

**背景**:用户在 SSH(远程模式)下预览服务器上的 PDF,希望文件重新生成后预览自动跟着变。服务器(HPC 集群)的 ssh 登录需要 Duo 二次验证(keyboard-interactive),后台 SFTP 连接用 BatchMode 永远登不上。

**决定**:
1. PDF 渲染从 Chromium 内置插件换成 **pdf.js**(`pdfjs-dist`,Apache-2.0,用 legacy 构建适配 Chromium 126)。Chromium 插件是黑盒 iframe,拿不到当前页码,文件一变只能回到第一页;pdf.js 的 `PDFViewer` 把位置(`updateviewarea`)和缩放(`scalechanging`)交出来,换文档后 `scrollPageIntoView` 回到原处。缩放只有按钮和 Ctrl+滚轮,不加快捷键(13.2)。
2. 文件变化用 **size + mtime 轮询**(`cmd:fs:stat-file`)而不是 fs.watch,与文件树一致;连续两轮相同才重读,避免读到 LaTeX 写了一半的文件。
3. 后台 SFTP 的 ssh 登录提示经 **askpass 中继**回到 Ceteris:`SSH_ASKPASS` 指向一个 C# 写的 5 KB 助手,第一次用到时由 Windows 自带的 csc.exe 编译到数据目录;助手经命名管道把提示交给 main,main 自动填保存的密码或把提示定向发给发起请求的窗口弹 modal。只有用户操作发起的连接允许弹窗;轮询发起的连接遇到提示直接断开并缓存为 `login-required`。
4. 原来的 `.cmd` askpass 助手移除。Windows 让 cmd.exe 解释 .cmd,而提示文本来自服务器,构成命令注入。先试过让 Ceteris.exe 自己当助手:Electron 的浏览器进程在 Windows 上启动时无条件往 stdout 写一个换行(`electron_main_delegate.cc`),ssh 读到换行就截断,答案永远为空,所以放弃。

**为什么不是别的方案**:
- 不用 ControlMaster 复用终端的连接:Windows 版 OpenSSH 不支持(`getsockname failed: Not a socket`,见 §14.3)。
- 不用 sshpass:它把 ssh 放到控制台上,破坏二进制 SFTP 流;而且它只会填密码,填不了 Duo。
- 不在本地终端里手敲 `ssh` 的 session 上做:Ceteris 不知道那条连接的主机和凭据,只能走远程模式。
- 不让 Chromium 插件保持页码:没有 API。

**放弃的**:pdf.js 没有配置 standardFontDataUrl / cMapUrl(file:// 页面不能再去取 file:// 资源),没内嵌字体的 PDF 用替代字体显示;助手依赖机器上有 .NET Framework 4.x 的 csc.exe(Windows 10 / 11 默认有),没有时文件树退回原来的 BatchMode 行为并记日志。

#### ADR-016:允许轻量编辑 txt 和 json,超大文件分段只读(2026-11-07)

**决定**:开发者要求在文件树里直接修改文本,覆盖 13.2 对内置文件编辑器的禁令。范围只有 .txt 和 .json,其余类型仍只显示。

- **2 MiB 以内**可编辑。更大的文件一次只读 256 KiB 一页,只读,靠滑块定位,所以几 GB 的文件也能立刻打开。
- **保存**只有按钮。Ctrl+S 属于 13.2 的应用内功能键,这条禁令不变。
- **写入**先写临时文件再 rename。文件在编辑期间被其他程序改过时拒绝保存,由用户选择覆盖或放弃。
- **未保存内容**留在 text-drafts.ts,不弹确认框。切换标签、关闭窗口、Link 重连(会 reload 窗口)都不丢内容,13.2 的"关窗不确认"不受影响。
- **只编辑 UTF-8**。保存总是写 UTF-8,所以 GBK、UTF-16 文件只读显示,不会被悄悄转码。换行符和 BOM 保存时还原。
- **SSH 标签页只读**,与 14.6 的 SFTP 只读浏览一致。Link 窗口可以编辑,保存由 Host 执行。

#### ADR-015:取消三栏分类,改用一个列表加标签(2026-11-06)

**决定**:侧栏只有一个文件夹列表。开过终端的文件夹自动加入并保留,只有用户能移除。第 4、5.1.1、8.2 节的收藏 / 临时 / 最近分类不再适用。标签用于筛选,选多个标签时取交集。

#### ADR-013:为什么 Linux 上"最后窗口关闭"允许阻塞 modal(v1.6,beta 反馈回合)

**背景**:Ceteris 第 2 章原则 4"窗口与应用解耦"在 Windows 上由系统托盘承载(关窗 → 沉托盘 → app 继续跑),在 macOS 上由 Dock 承载(关窗 → 留在 Dock,Electron 默认 `window-all-closed` darwin 分支不退出 = 原生 HIG)。两者共有"app 不死于窗口"的持久化位置。

**Linux 的根本问题**:GNOME 自 3.x 起官方移除 system tray,只能用社区 AppIndicator 扩展(用户侧负担、Wayland 下脆弱);若退而求其次走 GNOME Background Apps API,则仅 GNOME 44+ 支持,KDE/XFCE 没有。无论选哪个,都是"为支持 Ceteris 把代价转嫁给 Linux 用户"—— 违反 Linux"软件融入桌面环境"的传统。

**决策**:Linux 上 Ceteris 不做托盘 / 不做 Background Apps,**作为普通桌面 app 实现**(`lifecycleModel: 'no-persistence'`)—— 关闭最后一个窗口 = 应用退出,session 全销毁。配套**阻塞 modal 二次确认**作为唯一 UX 妥协:当最后一个窗口关闭且仍有 `state !== 'exited'` 的 session 时,弹 `确定关闭?N 个会话将终止 [取消/关闭]`;全灰则静默退出。

**为什么允许 modal,不是哲学倒退**:
- "窗口零成本开关"哲学的前提是"app 在别处常驻、关窗确实零代价"。Linux 无托盘 = 前提消失 = 最后窗口关闭不再零代价。
- modal 是**信息披露 + 确认门禁**,只在"会损失工作"时触发。非最后窗口关闭 / 全 exited session 时仍零成本,精神上的"廉价开关"对非最后窗口仍然成立。
- 三大主流 Linux 终端(gnome-terminal / konsole / xterm 系)都在有子进程时弹相似的确认 —— 这是 Linux 用户在终端语境下的既有期待。

**Windows / macOS 是否对称引入**:Windows 托盘菜单"完全退出"和 macOS `Cmd+Q` / App Menu Quit 已有(或应有)同语义二次确认。三平台共享同一 modal 组件(`<LastSessionConfirm />`),仅触发位置不同:
- Windows:托盘菜单"完全退出"按钮
- macOS:Cmd+Q / `before-quit` 事件
- Linux:最后一个窗口的 close 事件 + 上述非空条件

**为什么不走 daemon 架构彻底消灭这个 UX 妥协**:
- daemon(独立后台进程持有 PTY,Electron UI 仅是观察窗)能让 Linux 上 session 自然跨窗口存活,无需 modal。
- 但 daemon 要求主进程拆分、IPC 层重写、electron-builder 双产物、升级/崩溃恢复流程重设计 —— 工作量 2-3 倍 v1 现有架构。
- 收益评估:Windows / macOS 现有托盘 / Dock 模型已覆盖 daemon 的关窗存活收益,daemon 在两个平台上只剩"崩溃存活 / 升级存活"边缘改善(BETA-002 半解);Linux 上才是真正的架构升级。
- 结论:三平台架构对称比"为 Linux 单独 daemon"更重要,后者会演变成两套心智 / 两套代码。**v0.x / v1 不走 daemon**,留作 v2 评估窗口(详见第 15 章"演进路线 · daemon 候选")。

**对设计哲学的影响**:第 2 章原则 4 增加"Linux 平台例外"脚注;AGENTS.md 附录 C"关闭弹确认"硬规则增加同一例外脚注。两处都引回 ADR-013 作为论据来源。

**对实现的影响**:
- PlatformAdapter 新增 `lifecycleModel: 'tray-resident' | 'dock-resident' | 'no-persistence'` 字段(详见 12.2)。
- 主进程关窗事件处理按 `lifecycleModel` 分支:`tray-resident` 沉托盘、`dock-resident` 留 Dock(Electron 默认)、`no-persistence` 在最后窗口 + 非空 session 时弹 modal。
- modal 组件跨平台单一实现,触发条件三平台各异。

### 11.2 内存数据(守护进程)

为避免重复维护两套定义,主进程内的"对外可见"数据结构与 `src/shared/types.ts` 同源,以下为简化展示;`ManagedSession` 是 Main 内部 PTY/scrollback 句柄的容器,**不通过 IPC 暴露**,真实定义见 `src/main/session-manager.ts`。

```typescript
interface AppState {
  windows: Map<string, ManagedWindow>;     // windowId → window info(WindowManager)
  sessions: Map<string, ManagedSession>;   // sessionId → managed session(SessionManager)
  pathTree: {
    bookmarks: PathNode[];                 // 用户主动管理,持久化到 bookmarks.json
    temporary: PathNode[];                 // 自动:有 session 在跑且非收藏
    recent: PathNode[];                    // 自动:历史开过、当前不在临时也不在收藏(<= 30)
  };
  nextWindowNumber: number;                // 下一个窗口编号(单调递增,运行时分配,不持久化)
}

// ── IPC 暴露的部分 (shared/types.ts) ──────────────────────

interface WindowInfo {
  id: string;                              // UUID,持久且不复用
  number: number;                          // 显示给用户的编号 Window 1/2/...,关闭后不复用
  electronWindowId: number;                // BrowserWindow.webContents.id
}

interface SessionInfo {
  id: string;
  pathId: string;                          // session 创建时确定,**永不变**(ADR-008)
  templateId: string;
  originalCwd: string;                     // session 创建时的 cwd,永不变(ADR-008)
  currentCwd: string;                      // 实时 cwd(随 OSC 1337 更新);仅 UI ⚠️ 提示
  cols: number;
  rows: number;
  pid: number;                             // PTY 子进程 PID;-1 = 未 spawn 或已退出
  displayName: string;                     // 默认 = 模板名 / shell 名,后续可由用户改
  ownerWindowId: string | null;
  state: 'active' | 'idle' | 'exited';     // v1.2 起去 tombstoned(ADR-008)
  exitCode?: number;                       // exited 时
  exitedAt?: number;                       // exited 时,Unix ms
  createdAt: number;                       // Unix ms
}

interface PathNode {
  id: string;
  path: string;
  displayName?: string;
  category: 'bookmarked' | 'temporary' | 'recent';
  sessionIds: string[];                    // 创建顺序,push 追加,任何 owner 切换不会 reorder
  defaultTemplateId?: string;              // 仅收藏:双击新建终端的默认模板
}

// ── 主进程内部细节(不通过 IPC,见 session-manager.ts) ──

interface ManagedSession {
  info: SessionInfo;
  pty: IPty | null;                        // exited 后置 null
  outputSeq: number;                       // evt:session:output 单调序号
  scrollback: Buffer;                      // ring buffer,2 MB 上限,尾部裁切
  scrollbackLastSeq: number;               // scrollback 末尾对应的 outputSeq;给新 owner 拉历史 + 去重 evt
  parser: Osc1337Parser;                   // 每 session 一份,持有未完结 stash
  idleTimer: NodeJS.Timeout | null;        // active → idle
  cwdGraceTimer: NodeJS.Timeout | null;    // 启动 5s grace,到期未收 OSC 才进 polling
  cwdPollTimer: NodeJS.Timeout | null;
  oscReceived: boolean;                    // 一旦 true,所有 cwd 兜底永久关
  resizeQuietUntil: number;                // ConPTY 重绘 quiet 窗口截止 ts(CP-3 勘误 #3 v2)
  disposables: IDisposable[];              // PTY 监听句柄
}
```

**SessionInfo 与 ManagedSession 的边界**:`SessionInfo` 是经由 IPC 在 main / renderer 间传输的"外观",必须 JSON-safe;`ManagedSession` 是 main 进程内部对 PTY 句柄、ring buffer、计时器的容器,renderer 永远不接触。

### 11.3 数据持久化策略

* 写策略:任何状态变更触发 debounced 写入(500ms 节流)
* 写方法:写入临时文件 → fsync → rename(原子操作)
* 备份:每次成功写入后,保留前一份为 `.bak`
* 损坏恢复:启动时若主文件 JSON 解析失败,尝试 `.bak`;都失败则用默认值
* 版本迁移:settings.json 中的 `version` 字段控制迁移逻辑,未识别的版本拒绝加载

## 12. 跨平台策略

### 12.1 策略:Windows-first,but cross-platform-ready

Ceteris V1 只发布 Windows 版,作者只测试 Windows。但代码架构上为未来的跨平台扩展留好接口,让开源贡献者能在不修改核心代码的前提下添加 macOS / Linux 支持。

### 12.2 平台抽象层

```
src/main/platform/
  ├── index.ts          # 接口定义 + 平台分发
  ├── windows.ts        # Windows 实现(V1 完整实现)
  ├── macos.ts          # macOS 占位(throw "Not implemented")
  └── linux.ts          # Linux 占位(同上)
```

#### 抽象接口

```typescript
export interface PlatformAdapter {
  /**
   * 平台生命周期模型(v1.6,ADR-013)
   * - 'tray-resident'(Windows):关掉所有窗口后,app 仍跑在系统托盘,session 由托盘里的主进程持有。
   *   关窗事件:沉到托盘,不退出。完全退出走托盘菜单"完全退出"按钮(带二次确认 modal)。
   * - 'dock-resident'(macOS):关掉所有窗口后,app 仍在 Dock(Electron `window-all-closed`
   *   darwin 分支默认不退出 = macOS HIG)。完全退出走 Cmd+Q / App Menu Quit(带二次确认 modal)。
   * - 'no-persistence'(Linux):无托盘 / 无 Dock,关掉最后一个窗口 = 应用退出。
   *   当最后一个窗口关闭且仍有 state !== 'exited' 的 session 时,弹同一 modal 二次确认;
   *   全 exited 则静默退出。
   *
   * 三平台共享同一个 <LastSessionConfirm /> 组件,仅触发位置不同。
   */
  readonly lifecycleModel: 'tray-resident' | 'dock-resident' | 'no-persistence';

  /**
   * 检测系统中可用的 shell
   * Windows: pwsh.exe / powershell.exe / cmd.exe / Git Bash
   * macOS: zsh / bash / fish
   * Linux: 读 /etc/shells
   */
  detectShells(): Promise<ShellInfo[]>;

  /**
   * 给定一个 shell,返回启动它时需要的额外参数和环境变量,
   * 以便注入 OSC 1337 cwd hook
   */
  buildShellLaunchParams(
    shell: ShellInfo,
    hookFilePath: string
  ): { args: string[]; env: Record<string, string> };

  /**
   * 注册 / 注销文件管理器右键集成
   * Windows: 注册表 HKCU\Software\Classes\Directory\shell\... + MSIX sparse
   * macOS: Finder Sync Extension(Swift,需独立子项目)
   * Linux: **不写 Nautilus 扩展**(nautilus-python 依赖重 + GTK 版本兼容性差)。
   *   走 freedesktop 标准:安装 .desktop 文件 + Categories=TerminalEmulator;
   *   用户在 Ceteris 设置→系统集成点"设为默认终端"时,跑 gsettings
   *   org.gnome.desktop.default-applications.terminal exec + update-alternatives
   *   (或 RHEL/CentOS 的 alternatives)。所有 GTK 文件管理器(Nautilus / Nemo / Caja)
   *   的"在终端中打开"会自动用 Ceteris。详见 ADR-013 与 BETA-003 实施计划。
   */
  registerFileManagerIntegration(appExePath: string): Promise<void>;
  unregisterFileManagerIntegration(): Promise<void>;

  /**
   * 查询进程的当前工作目录(OSC 1337 hook 失败时的兜底)
   * Windows: NtQueryInformationProcess + 读 PEB
   * macOS: proc_pidinfo
   * Linux: readlink /proc/<pid>/cwd
   */
  getProcessCwd(pid: number): Promise<string | null>;

  /**
   * 设置开机启动
   */
  setAutoStart(enabled: boolean): Promise<void>;
  isAutoStartEnabled(): Promise<boolean>;
}
```

### 12.3 跨平台礼仪

为了让未来贡献者方便,V1 代码必须遵守:

1. **不硬编码平台特定 API** — 通过 PlatformAdapter
2. **不硬编码路径分隔符** — 用 `path.sep` / `path.join`
3. **不硬编码行结束符** — 用 `os.EOL`
4. **不硬编码用户目录** — 用 `app.getPath('userData')`
5. **不硬编码 socket 路径** — 通过 PlatformAdapter
6. **平台特定逻辑都加注释** — 写清"其他平台思路"
7. **`window-all-closed` 按 `lifecycleModel` 分支处理**(v1.6,ADR-013):
   - `tray-resident`(Windows):不退出,沉到托盘
   - `dock-resident`(macOS):不退出,Electron darwin 默认行为(留在 Dock)
   - `no-persistence`(Linux):若仍有 `state !== 'exited'` 的 session,弹 `<LastSessionConfirm />` modal;用户确认后 `app.quit()`;全 exited 则直接 `app.quit()`

### 12.4 跨平台准备的额外文件

* `electron-builder.yml`:三平台 target 模板齐全,只 Windows 启用
* `.github/workflows/release-windows.yml`:Windows CI
* `.github/workflows/release-macos.yml.template`:macOS CI 模板,贡献者改名启用
* `.github/workflows/release-linux.yml.template`:Linux CI 模板
* `CONTRIBUTING.md`:说明 PlatformAdapter 设计哲学,引导新平台贡献

### 12.5 Shell Hook 文件

为各 shell 准备的 hook 文件全部在 `src/shell-hooks/` 提交:

* `pwsh.ps1` — PowerShell(V1 实现并测试)
* `cmd.bat` — cmd.exe(V1 实现并测试)
* `bash.sh` — bash(V1 已写好但不主动启用,留给 Mac/Linux 贡献者)

* `fish.fish` — fish(占位)

每个 hook 文件做两件事:
1. 加载用户原本的配置(rc 文件 / profile)
2. 注入 OSC 1337 prompt hook

## 13. 非目标(明确不做的事)

### 13.1 V1 不做(为 V2+ 留)
* 多 UI 同步同一 session(只做单 owner 模型)
* WSL session 支持
* 标签页拖拽改顺序 / 拖出新窗口
* 自动下载和安装更新(v1.11 起会检查新版本并给出直链,下载和安装仍由用户自己做,见 ADR-018)
* 应用打开时恢复上次窗口布局
* 状态识别中的"等待输入"和"错误"(只做活跃/空闲/已退出)
* 系统通知
* 已退出 session 重启(若需要"再跑一次",在同一 path 新建一个 session,见 ADR-008)

### 13.2 永远不做(违反产品哲学)
* 应用内功能键(任何不在 §7.2.2 终端键位清单内的快捷键)— 违反"鼠标优先";例:Ctrl+T 新 tab / Ctrl+W 关 tab / Ctrl+Tab 切 session / Alt+1..9 跳 tab / 任何菜单加速键
* 全局快捷键 — 同上
* 命令输入框输入路径 — 违反"路径只能点击"
* "主窗口"概念或任何窗口的特殊地位 — 违反"窗口平等"
* 关闭单个窗口的确认对话框 — 违反"窗口平等",窗口应是零成本开关
* Project / Workspace / Repo 等容器层级 — 违反"路径中心"
* 跨 session 上下文累积 / kanban / workstream — 违反"session 用完即弃"
* 内置 AI 助手或 chat 界面 — 让 agent 自己做 agent
* 远程 SSH session 管理 — 不是产品定位
* 通用文件编辑器 — 不是产品定位。例外:txt、json、tex、Markdown,以及代码和数据文件(R、Python、Julia、Stata、SQL / HiveQL 等,清单在 `src/shared/code-files.ts`)的轻量编辑和保存后 lint,见 ADR-016、ADR-028、ADR-040。格式化、补全、跳转定义这类 IDE 功能仍然不做
* 设置的"保存"按钮 — 违反"即改即生效"

### 13.3 不会自己做但欢迎社区贡献
* macOS 实现
* Linux 实现
* WSL 集成
* 更多 shell hook(fish, nushell, xonsh, ...)
* 主题方案扩展(目前 7 套已足够)
* i18n 国际化(V1 中英双语已包含)

## 14. 远程 SSH 模式

> **状态**:v1.7(2026-05-25)落地 M1 = 0.2.0 GA 候选。详细方案见
> `docs/archive/方案-SSH-完整支持-20260524.md`,本章是已实施部分的规范快照。

### 14.1 总体定位

**Ceteris = 终端管理器(本地 + SSH 远程终端)。** 文件能力只服务于终端:看当前目录、选文件夹、看 PDF,边界见 §14.6。

### 14.2 本地用户感受

2026-11-05 起远程入口始终显示:Sidebar 顶部的 `[本地] [远程]` 和设置页的"远程"分类
不再隐藏,`advanced.enableRemote` 已移除。开发者决定让 SSH 成为默认能力,这取代了
原来"不开 SSH 时 UI 与 beta.9 一致"的不变式。

仍然成立的部分:
- 没有 SSH 服务器时,本地路径、三栏分类和终端行为不受影响
- 启动时间、内存占用无变化:SSH 相关模块(ssh-config 解析、known_hosts、ssh-agent
  探测、SFTP 连接)按需触发,不在启动期消耗

### 14.3 SSH 模式范围

**V1 主线 / M1(= 0.2.0 GA)已落地**:
- profile 管理(CRUD + 编辑 + 密码加密保存,走 Electron `safeStorage`)
- ssh_config 集成(读 `~/.ssh/config` 的 Host + Include,合并显示;Match 跳过)
- 完整认证矩阵:密钥文件 + 密钥文件选择器 + ssh-agent 探测 + 保存密码(可选)
- ProxyJump 多级跳板(`-J host1,host2,host3`)
- known_hosts 浏览器 + 指纹历史(指纹变化时高亮 potential MITM)
- ControlMaster 连接复用(默认开启,~3s → <100ms / session)。只在 Linux / macOS 生效:Windows 版 OpenSSH 收到 ControlMaster=auto 会以 `getsockname failed: Not a socket` 退出,Windows adapter 因此不传这组参数
- 远程 tmux per-launch attach-or-create + 智能 session 命名
- 重连按钮(SSH session 退出后手动重连,同 pathId + 同 templateId)

**V1.1 / V2(暂不做,等用户反馈决定)**:
- HostKeyPromptModal — 拦截 ssh 首次连接 `Are you sure...` prompt
- MFA / TOTP modal — 截获 verification code prompt
- 自动重连 + 网络变化检测(`navigator.onLine` + `powerMonitor`)
- 远端 tmux session 列表面板(只看不操作)
- **远程文件编辑、上传、删除**:属于文件管理范畴(详见 §14.6)
- **端口转发**(本地 / 远程 / 动态 SOCKS5)— 属于网络工具范畴

**永远不做**:
- X11 forwarding(罕用,跨平台 X server 噩梦)
- VPN 集成
- GUI 转发

### 14.4 类型系统约束

1. `PathKind = 'local' | 'ssh'` 是 discriminated union,`kind` 字段**必填**
2. `Bookmark / RecentEntry / PathNode` 都是 `LocalX | RemoteX` union,ssh
   变体里 `sshProfileId: string` 必填
3. 每个使用 `Path` 的函数必须 `switch on kind` exhaustive 覆盖,
   `assertNeverPathKind(value: never)` 兜底
4. 旧磁盘数据(beta.9 之前,无 kind 字段)由 `PathManager.initialize` 走
   `migrateBookmarkOnLoad` / `migrateRecentOnLoad` flatMap 自动 coerce 为
   local;损坏 ssh 条目(kind=ssh 缺 sshProfileId)启动期静默丢弃,导入
   archive 走严格校验直接拒
5. CI Gate 拦截破坏 exhaustiveness 的代码

### 14.5 共用 vs 独立的划分原则

- **通用概念共用**:`Path` / `Session` / `Bookmark` / `Recent` → 共用
  Manager,内部 switch on kind 分支
- **SSH 专属概念独立**:`SshProfile` / `KnownHost` / `SshAgent` /
  `ControlMaster` / `SftpPool` / `PortForwardManager`(未来)
  没有"本地版本",走独立模块(`src/main/ssh-profile-manager.ts` /
  `ssh-config-parser.ts` / `ssh-agent.ts` / `known-hosts-manager.ts`)
- **UI 层**:本地与远程入口走 segmented + filter 分离;组件级别按需共用
  (TerminalView 同一组件渲染本地 / SSH session,内部按 `pathId.startsWith('ssh:')`
  做小分支)

### 14.6 文件管理 vs 终端管理分离原则

Ceteris 的产品边界画在"终端"上,**不延展到"文件管理"**:

1. **在做的**:本地终端、SSH 远程终端、远程 tmux、终端搜索、终端复制粘贴,以及
   服务于这些终端的只读文件能力(见下方例外条款)
2. **不做的**(文件管理):远程文件编辑 / 上传 / 删除 / 文件拖拽上传 /
   远端 Explorer 集成

理由:
- 文件管理是另一个产品形态(WinSCP / FileZilla / Termius 的文件面板),做了
  等于让 Ceteris 兼任两类产品职责
- "路径中心"概念在 Ceteris 里指**会话**,不指**文件浏览**;加 SFTP 会让
  "路径"变成"会话 + 文件浏览"双中心
- 用户已有成熟的文件管理工具,Ceteris 不做不影响 SSH 终端的核心可用性

**例外条款**:
- 本地文件树(2026-11-05 开发者决定):侧栏可显示当前 session 所在的本地目录,支持查看和重命名,不做编辑、删除、移动
- 本地文件树删除(2026-11-10 开发者决定,推翻上一条的"不做删除"):右键本地文件或文件夹可"删除",只移到回收站 (`shell.trashItem`),不永久删除,不弹确认;回收站就是撤销。远程文件仍不能删除。同日加入右键"在文件资源管理器中打开"
- 远程文件浏览(2026-11-05 开发者决定,推翻原来的"必须走独立窗口"):SSH session 使用同一个侧栏文件树,通过 SFTP 只读浏览,不提供重命名;添加远程文件夹时用 SFTP 选择框代替手动输入路径
- PDF 查看(2026-11-05 开发者决定;v1.10 改用 pdf.js,ADR-017):在文件树点击 PDF,盖在该 session 的终端区域上显示,终端在下面继续运行。只读,不是文件编辑器。显示期间轮询文件的大小和修改时间,文件被重新生成后自动重读,页码、位置和缩放保持不变(LaTeX 式"改一行编译一次"的工作流)。图片和 markdown 同样自动刷新
- 文件显示位置(2026-11-07 开发者决定):只有一个终端时,文件在左,终端在右。有空窗格时占用空窗格。窗格全满时盖住所在窗格,关闭后露出终端
- txt 和 json 编辑(2026-11-07 开发者决定):见 ADR-016。tex 和 Markdown 编辑(2026-11-08 开发者决定):见 ADR-028
- 端口转发不算"文件管理",但属于"网络工具",同样不在 V1 主线,降为 V2 可选

### 14.7 数据模型摘要

- `ssh-profiles.json`:`{ version: 1, profiles: SshProfile[] }`,
  密码经 `safeStorage` 加密为 `passwordEncrypted: string`(base64),renderer
  副本剥去明文 / 加密字段,只保留 `hasSavedPassword: boolean`
- `known-hosts-history.json`:`{ version: 1, entries: [{ host, timeline:
  [{ fingerprint, keyType, firstSeenAt }] }] }`,跨重启保留
- `bookmarks.json` / `recent.json`:磁盘 schema(`PersistedBookmark` /
  `PersistedRecentEntry`)kind 可选;内存严格类型(`Bookmark` / `RecentEntry`)
  kind 必填,由迁移层桥接

### 14.8 设置项

- `advanced.includeSshConfig: boolean`(默认 false)— 读 `~/.ssh/config` 合并到
  profile 列表
- `advanced.enableControlMaster: boolean`(默认 true)— OpenSSH ControlMaster
  连接复用

### 14.9 SFTP 实现约束

- 走系统 `ssh -s sftp`,协议编解码在 `sftp-protocol.ts`。不用 `sftp` 程序:Windows 版在 stdout 是管道时全缓冲,进程不退出就读不到输出,而且会吞掉 ssh 的报错。不用 npm 库:ssh_config、agent、ProxyJump、known_hosts 必须和终端一致
- 每个 profile 一条常驻连接,空闲 5 分钟关闭,文件树的轮询不重复握手。**例外(v1.10)**:登录时问过用户(密码 / Duo / 主机密钥)的连接不做空闲关闭,每次重连都是一次 Duo 推送
- **登录提示走 askpass 中继(v1.10,ADR-017)**:Windows 上 ssh 以 `BatchMode=no` 启动,`SSH_ASKPASS` 指向一个用 Windows 自带的 csc.exe(.NET Framework 4.x)第一次用到时编译出来的 5 KB 助手 exe(源码在 `askpass-helper-source.ts`,产物在数据目录 `askpass/` 下按哈希命名),`SSH_ASKPASS_REQUIRE=force`。ssh 需要输入时启动助手,助手经命名管道(`\\.\pipe\ceteris-askpass-<pid>-<随机>`,每条连接一个随机令牌)把提示交回 main。main 按 `askpass-policy` 决定:保存的密码自动填一次(密码只走管道,不进命令行也不进环境变量);**用户操作发起的连接**(挂载文件树、点重试、点击文件、打开选择框,IPC 带 `interactive` / `fresh`)把提示定向发给那个窗口弹 modal;**定时轮询和自动刷新发起的连接**遇到提示直接断开,记为 `login-required`,不弹窗、不发凭据。助手必须是真正的 exe:.cmd 由 cmd.exe 解释,而提示文本来自服务器,`&calc` 这样的提示就能在用户机器上执行命令(CVE-2024-24576 的形态);Ceteris.exe 自己也不行,Electron 在 Windows 上启动时无条件往 stdout 写一个换行,ssh 读到换行就截断。没有 csc.exe 时退回 BatchMode。没有中继的平台(macOS / Linux 适配器未实现 `prepareSshAskpass`)保持原样:BatchMode=yes,保存了密码时用 sshpass
- 连接失败要缓存,防止轮询反复登录触发 fail2ban。认证、主机密钥、缺少 sftp 子系统和 `login-required` 的失败不自动重试,等用户明确操作(打开选择框、点重试、点 PDF;挂载文件树也算,它允许弹提示但不跳过缓存)或改 profile。网络失败 30 秒后重试
- 服务器不可信:限制包长、stderr、目录读取时间,丢弃不合法的文件名,拒绝超过请求大小的 DATA
- 只发只读请求,OPEN 只用读标志
- PDF 每块 1 MiB:Link 单帧上限 8 MiB,命令超时 30 秒。读取命令只读普通文件,限定可查看的扩展名,每块都检查文件头,响应带 size 和 mtime 作为自动刷新的基线
- **自动刷新用 size + mtime 轮询,不用 fs.watch**(v1.10):`cmd:fs:stat-file` 与文件树轮询同一原则(WSL UNC 路径上 fs.watch 不可靠,远端更没有 watch)。本地 1.5 秒、远端 3 秒,窗口不可见时跳过;stat 连续两轮相同且与基线不同才重读,避免读到写了一半的文件;重读失败保留旧内容并显示可点的"无法刷新"。stat 和自动重读永远不带 `fresh` / `interactive`
- 窗口只显示应用页面:`will-navigate` 全部拦截,链接交给系统浏览器(pdf.js 的外链 target=_blank → `setWindowOpenHandler` 只放 http(s));`handleCommand` 拒绝不是来自应用页面的 IPC,拿不到发送方 frame 时同样拒绝。换用 pdf.js 后不再需要 `plugins: true`、`frame-src blob:` 和 Chromium PDF 扩展的 CSP 豁免,CSP 新增 `worker-src 'self' blob:` 给 pdf.js 的解析线程

* WSL session 一等公民

### 演进路线 · daemon 候选(评估窗口:v2.0+)

**触发条件**:任一成立时考虑立项
- BETA-002 类崩溃导致用户实际损失工作的频率 > 月 1 次
- 升级 Ceteris 时丢 session 成为社区反馈高频项
- Linux 用户对"最后窗口 modal"持续不满,要求 session 跨窗口存活

**架构变更概要**(详细评估留给真正立项时):
- 拆 Electron 主进程为 **daemon(后台常驻,持有所有 PTY)** + **UI(Electron 窗口,通过 named pipe / 本地 socket 连 daemon)** 两份产物
- Windows:daemon 跑成 Windows Service(或退而求其次 detached process,登录态活)
- macOS:daemon 跑成 launchd LaunchAgent
- Linux:daemon 跑成 systemd --user service —— 顺带消灭 ADR-013 的"最后窗口 modal"
- IPC 协议升级支持 UI 端断连重连、session 接管

**为什么 v1 不做**:
- 工作量 2-3 倍于现有主进程架构,需重写 IPC、持久化、单实例、升级流程
- Windows / macOS 现有 tray / Dock 模型已覆盖 daemon 大半收益(关窗存活),边缘改善(崩溃存活 / 升级存活)不足以驱动整体架构重做
- 三平台同步演进比"仅 Linux daemon"更重要 —— 后者会变成两套架构维护两套心智

**为什么不彻底否决**:
- daemon 是 Linux 优等公民方案(对齐 tmux/screen 心智),长期价值在
- 真正解决 BETA-002 系列崩溃丢 session
- 留作 v2 候选,而不是"永远不做"

## 附录 A:术语表

| 术语 | 定义 |
|------|------|
| Path | 用户的"工作位置",一个文件系统目录 |
| Session | 一个 PTY 进程及其状态,包括 shell + 可选的子命令(如 claude code) |
| Window | Ceteris 的一个 UI 窗口实例,临时的观察工具,可任意开关,所有窗口完全平等 |
| 应用 / 守护进程 | Ceteris 的本体,持有所有 PTY 和数据;Electron Main Process;生命周期独立于任何窗口 |
| 纯托盘模式 | 应用在运行但 0 窗口的状态 |
| Owner Window | 当前持有某 session 字节流推送权的窗口,任一时刻最多一个 |
| 无主 Session | 当前无 owner window 的 session,在守护进程内继续运行 |
| OSC 1337 | iTerm2 定义的 ANSI 序列扩展,用于 shell 与终端的元数据通信 |
| Scrollback | 终端的历史输出缓冲区,新 owner 切换时需要重放 |
| Hook | 注入到 shell 启动流程中的脚本,负责发出 OSC 1337 序列 |
| Exited Session | Session 进程已退出但 UI 上仍可见的状态,无时限保留直到用户右键关闭(自 v1.2 起取代原"墓地期"概念,见 ADR-008) |
| originalCwd | Session 创建时的 cwd,等于该 session 所属 path 的 path 字段,生命周期内不变 |
| currentCwd | Session 内 OSC 1337 实时报告的工作目录,与 originalCwd 不一致时标签显示 ⚠️ |
| `replaceAll()` | 各 Manager(Settings / Path / Templates)v1.3 新增的方法,用于设置导入时整体替换内存数据 + 持久化 + emit 事件,**不重启应用**(见 ADR-009) |
| Local Font Access API | Chromium 提供的 `window.queryLocalFonts()`,枚举系统已安装字体;Electron 通过 `setPermissionRequestHandler` 自动放行 `local-fonts` 权限(v1.3 启用) |
| Resize Quiet 窗口 | `pty.resize` 后 500 ms 内 PTY 输出视为 ConPTY 重绘回声,**不触发 markActive**(只更新 scrollback / emit output);防 idle session 切窗口时 tab 闪绿(CP-3 勘误 #3 v2) |

| tmux / zellij | Unix | session 持久化的鼻祖,但 TUI 不是 GUI |
| Nimbalyst | 跨 | Workspace + Kanban,但偏团队协作,与 Ceteris 哲学相反 |
| Claude Code Desktop | 跨 | Anthropic 官方,但绑定 Claude,不通用 |

## 附录 C:决策历史

本文档是经过约 25 轮深度讨论后的产物,关键设计决策的演化:

1. 起点:解决"多 agent 并发跑会忘记某个"的实际痛点
2. 拓展:意识到痛点不限于 agent,普通终端也有
3. 关键转向 1:从"多 UI 同步 session"砍成"单 owner + 跨窗口聚焦",架构复杂度降至 1/3
4. 关键转向 2:从 project 中心改为 path 中心,匹配真实工作流
5. 关键转向 3:确立"session 用完即弃"哲学,不维护跨会话上下文
6. 关键发现:Windows 平台的此类组合无对手,微软自己都没解决基础需求(close to tray)
7. 跨平台策略:从"做跨平台"调整为"架构 ready,实现交给社区"
8. 主题系统:复用作者已有的 Rose Pine 5 主题方案,带 #f0f fallback 机制
9. 不做应用内快捷键:保持鼠标优先工作流,避免向"键盘原教旨主义"妥协
10. **(v1.1 修订)** 修正"主窗口"概念错误,确立"所有窗口完全平等"模型;关闭窗口不影响应用,应用退出仅来自托盘菜单
11. **(v1.1 新增)** 设置页面完整规格;即改即生效无保存按钮
12. **(v1.2 修订,ADR-008)** path 与 cwd 解耦 — session.pathId 创建后永不变;cd 仅在标签上加 ⚠️ 提示,不再驱动 path 在分类间迁移
13. **(v1.2 修订,ADR-008)** 砍掉 5 分钟墓地自动过期 + 重启功能;session 进程退出后进入 Exited 灯显态,无时限保留,直到用户主动关闭
14. **(v1.3 修订,ADR-009)** CP-4 勘误回合一次性确立 6 项与实际工程的对齐:主题 5→7 套(加 Ubuntu / Windows Terminal);移除 followSystemTheme(`nativeTheme.shouldUseDarkColors` 在 Windows 不可靠);字体下拉走 `queryLocalFonts`;UI 系统图标改 lucide-react;设置导入改 in-memory replace 不重启应用(原 `app.relaunch` 在 dev 模式失效);CSP via webRequest header(取代 meta CSP)。
15. **(v1.4 修订,ADR-010/011)** Milestone 1 内部上线大优化 — `frame:false` + 自绘标题栏 + macOS/Windows 双布局选项;14 项 daily driver 必需的工程改进(右键菜单完整化 / 拖文件夹到终端区 / 主进程 uncaughtException 兜底 / 持久化日志 / 应用图标 / 导出归档隐私 / 窗口位置记忆 / 托盘菜单完整化 + 动态图标 / 启动期 grace / Ctrl+滚轮字号 / env 遮罩 / Toast 通知 / 不可达路径处理 / 单实例聚焦)。
